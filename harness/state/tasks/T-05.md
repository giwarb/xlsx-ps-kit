# T-05 Clear-XlsOrphans

## 目的
クラッシュ等で残った「自モジュールが起動した」EXCEL.EXE だけを回収する `Clear-XlsOrphans` を実装する。

> 02-implementation-plan.md: 「孤児プロセス回収 `Clear-XlsOrphans`(自モジュール起動 PID のみ)」
> 01-design.md §3.1: 起動した PID を `$env:TEMP\xlsagent\<pid>.marker` に記録(finally で削除)。
> → 正常終了したセッションのマーカーは残らない。残っているマーカー = 異常終了の候補。

## 入力
- 参照ファイル: docs/01-design.md §3.1、docs/03-guardrails.md G-10
- 前提タスク: T-03(完了済み。マーカー方式・PID+開始時刻による所有権照合が確立済み)
- 前提レビュー: harness/state/reviews/T-02.md(所有権証明の考え方)、T-03 系

## 仕様(確定分+実装判断)
- `$env:TEMP\xlsagent\*.marker` を走査。
- 各マーカーの PID について:
  - プロセスが存在しない → マーカーだけ削除(ゴミ掃除)。
  - プロセスが存在し EXCEL.EXE である → 停止して マーカー削除。
  - プロセスが存在するが EXCEL.EXE でない(PID 再利用)→ 停止せずマーカーだけ削除。
- G-10: 全殺し禁止。マーカーにない PID には一切触れない。fail closed(疑わしきは殺さない)。
- マーカーに開始時刻等の照合情報を含める必要があれば、T-03 のマーカー書式を拡張してよい(その場合は Invoke-XlsSession 側の書き込みも合わせて更新し、実装メモに記録)。
- 戻り値: 回収した PID / 掃除したマーカーの一覧(オブジェクト)を返す(エージェントが結果を確認できるように)。

## 受け入れテスト要点(test-plan.md)
- 自 PID のみ回収、他 PID は残す:
  - 死んだ PID のマーカー → マーカーが消える。
  - EXCEL でないプロセスの PID を指すマーカー(例: 自テストが起動した notepad や powershell の PID)→ プロセスは生存のまま、マーカーだけ消える。
  - マーカーのない実行中プロセスには触れない。
  - (可能なら)Invoke-XlsSession の ScriptBlock 実行中に別スレッド/プロセスから見るとマーカーが存在する、正常終了後は消えている(T-03 でテスト済みなら省略可)。
- 「生きた孤児 EXCEL」の再現はリスクがあるため必須としない(強制終了経路は T-02 でテスト済み)。やる場合は安全策を実装メモに書く。

## 実装メモ(Sonnet が記入)

### やったこと

- `skill/scripts/XlsAgent.psm1` の `Clear-XlsOrphans` を実装。`$env:TEMP\xlsagent\*.marker` を走査し、
  各マーカーを次の優先順位（上から順に最初に該当したもので確定、fail closed）で判定する:
  1. マーカー 1 行目から PID を解析できない -> 停止せずマーカーのみ削除（`Skipped-InvalidMarker`）。
  2. その PID のプロセスが存在しない -> 停止せずマーカーのみ削除（`Skipped-DeadPid`）。
  3. プロセスは存在するが `EXCEL` ではない（PID 再利用で別プロセス） -> 停止せずマーカーのみ削除
     （`Skipped-NotExcel`）。
  4. プロセスは `EXCEL` だが、マーカーに記録した開始時刻と実際のプロセス開始時刻が一致しない
     （PID 再利用で別の EXCEL.EXE、ユーザーが新しく開いた正規の Excel の可能性を含む） -> 停止せず
     マーカーのみ削除（`Skipped-Unverified`）。
  5. プロセスが `EXCEL` で開始時刻も一致する（自モジュール起動の本人だと確認できた） -> `Stop-Process
     -Force` で停止し、消滅を確認してからマーカー削除（`Stopped`）。`-WhatIf` 指定時はここで
     `Stop-Process` も呼ばずマーカーも残す（`WhatIf-WouldStop`）。
  戻り値は `PSCustomObject`（`Pid` / `MarkerPath` / `Action`）の配列（マーカーなしなら空配列。
  `Get-ExcelPids` と同じ `return , $results` パターンで `$null` 化を防いでいる）。
- マーカー書式を拡張（判断・実装）: 1 行目 PID、2 行目 プロセス開始時刻（UTC Ticks、
  `Start-XlsApplication` が記録する `XlsAgentProcessStartTicks`）。`Invoke-XlsSession` の
  `Set-Content -Value $app.XlsAgentProcessId` を `-Value @($app.XlsAgentProcessId,
  $app.XlsAgentProcessStartTicks)` に変更し、書き込み側も合わせて更新した。
  理由: PID だけでは「クラッシュ後にその PID が別の EXCEL.EXE（ユーザーが新しく開いた正規の Excel を
  含む）に再利用された」場合に、プロセス名一致だけで誤って停止してしまう。`Stop-XlsApplication` が
  強制終了直前に PID + 開始時刻の両方を照合しているのと同じ考え方（T-02 round 1 レビュー指摘）を
  `Clear-XlsOrphans` にも持たせた。旧（1 行だけの）マーカーは 2 行目がないため
  `recordedStartTicks = $null` となり、EXCEL.EXE であれば自動的に「開始時刻を確認できない」＝
  `Skipped-Unverified`（停止しない）側に倒れる。fail closed の方向に安全に効くので後方互換上の
  問題はない。
  回帰確認: `Invoke-XlsSession.Tests.ps1` の「writes a PID marker ... then removes it」テストは
  `Test-Path` で存在確認するだけで中身を検証していないため、この書式変更でも無修正で緑のまま。
  全体回帰（下記）でも確認済み。
- `tests/Clear-XlsOrphans.Tests.ps1` を新規作成。COM は一切直接触らない（Clear-XlsOrphans 自体が
  COM を使わないため）。「生きた EXCEL」が絡む 2 ケースだけは、公開関数 `Invoke-XlsSession` を
  別 STA runspace で呼ぶことで COM 操作を ScriptBlock 内に閉じ込める（T-03 の (b) と同じパターン、
  ヘルパー `New-BackgroundXlsSession` / `Stop-BackgroundXlsSession` に切り出した）。
  - 死んだ PID のマーカー -> 削除される（`Skipped-DeadPid`）。
  - 解析できないマーカー -> 削除される（`Skipped-InvalidMarker`）。
  - 自分で起動した無害な `powershell.exe`（`Start-Sleep`）の PID を指すマーカー -> プロセスは生存、
    マーカーのみ削除（`Skipped-NotExcel`）。試験後は `finally` で必ず `Stop-Process`。
  - マーカーのない実行中プロセス（同じく自分の `powershell.exe`）は結果に一切現れない。
  - **G-10 の核心（fail closed）を、実際の孤児を作らずに安全に検証**: `New-BackgroundXlsSession` で
    本物の EXCEL.EXE を起動・保持（＝きちんと `Invoke-XlsSession` に所有されている、孤児ではない）
    したまま、そのマーカーの 2 行目（開始時刻）だけを意図的に書き換えて「PID は合うが開始時刻が
    合わない」状態を作る。`Clear-XlsOrphans` がそれを停止しないこと（`Skipped-Unverified`）を
    確認する。
  - 「PID も開始時刻も一致する（=本来は停止対象）」の判定ロジックは `-WhatIf` を使い、実際には
    `Stop-Process` を呼ばずに `WhatIf-WouldStop` が返ることだけを確認する（安全策）。
  - 「生きた孤児 EXCEL を実際に強制終了する」テストは書いていない（タスクカードで必須外と明記。
    T-02 で `Stop-XlsApplication` の強制終了フォールバック自体は既にテスト済み）。
- `tests/T01.Tests.ps1` の `$script:StillStubFunctions` から `Clear-XlsOrphans` を除外（T-03/T-04 で
  確立済みの「実装済み関数はスタブ throw 検査から外す」パターンを踏襲。除外しないと、
  `Clear-XlsOrphans` に残る `Stop-Process` 失敗時の `throw` に偶然引っかかって緑になり、
  「未実装スタブである」ことを検証するはずのテストが意味を失う）。

### 踏んだ COM の罠（今回は COM を直接触らないため、COM そのものの罠は新規になし）

- ファイル I/O の罠（COM ではないが今回踏んだ）: 新規に作った `.ps1` を `Write` で保存すると
  UTF-8 BOM なしになり、日本語コメントを含む状態で PowerShell 5.1 がパースに失敗した
  （`Missing ')' in method call.` 等、無関係に見える箇所でパースエラーが出る）。既存ファイルは
  すべて `EF BB BF` の BOM 付きだったため、`[System.IO.File]::WriteAllText(path, content,
  (New-Object System.Text.UTF8Encoding($true)))` で BOM 付きに書き直して解消した。今後 `Write`
  ツールで新規 `.ps1`/`.psm1` を作るときは、保存後に BOM の有無を確認すること。
- テストの罠: `return , $results`（`Get-ExcelPids` と同じ「空集合でも $null にしない」パターン）で
  実装した関数を呼ぶテスト側で `$result = @(Clear-XlsOrphans)` のように呼び出し全体を **さらに**
  `@()` で包むと、二重に配列化されてしまう（外側の `@()` が、既にコンマ演算子で「1 個の出力」として
  保護されている戻り値そのものを、もう一段配列に包んでしまうため）。結果、`$result.Count` が常に 1
  になったり、`$result | Where-Object { $_.Pid ... }` で `$_` が配列自身になり
  `The property 'Pid' cannot be found on this object.` という一見無関係なエラーになった。
  `Get-ExcelPids` の既存の呼び出し側（`Assert-NoOrphanExcel` 内 `$current = Get-ExcelPids`）と同じく、
  呼び出し側では `@()` を重ねずに素で代入する（`$result = Clear-XlsOrphans`）のが正しい。

### round 1 レビュー（`harness/state/reviews/T-05.md`、判定 `fix`、blocking 2件）への対応

指摘ごとに「対応した／対応しない（理由）」を記録する（G-16）。

1. **[blocking] マーカーは所有権を示しても「孤児」であることを示さない** — **対応した。**
   下の「設計上の既知の限界」に書いていた内容（正常進行中のセッションを孤児と誤認しうる）は、
   実装メモに書くだけで済ませてよい話ではなく、`Clear-XlsOrphans` の関数契約そのものを破る問題
   だったため、レビュー指摘どおり修正した。`Invoke-XlsSession` が PID/開始時刻を書き込んだ
   `FileStream` を `[IO.FileShare]::None` のまま `finally` まで開いたまま保持する（OS レベルの
   排他リース）よう変更し、`Clear-XlsOrphans` は各マーカーをまず `[IO.File]::Open(...,
   FileShare.None)` で排他オープンできるかどうかを最初に確認するようにした。共有違反（進行中の
   正常なセッション）なら `Skipped-ActiveSession` として一切手を触れない。ホストプロセスが
   クラッシュすれば OS がハンドルを自動的に解放するため、真の孤児だけが排他オープンに成功し、
   従来どおり PID・プロセス名・開始時刻の照合に進める。
   レビュー指摘の再現テストどおり、`tests/Clear-XlsOrphans.Tests.ps1` に
   「正常なバックグラウンドセッションに `-WhatIf` なしで `Clear-XlsOrphans` を呼び、プロセスも
   マーカーも変化せず `Skipped-ActiveSession` になる」テストを追加した（`-WhatIf` を付けても
   同じ結果になることを確認する補助テストも追加）。
   これに伴い、旧「設計上の既知の限界」節はもう成立しないため削除した（下記参照）。
2. **[blocking] 照合した Process とは別に PID を再解決して停止している** — **対応した。**
   `ShouldProcess` を通過した直後に、照合に使った同じ `Process` オブジェクトへ `Refresh()` を
   呼び、`HasExited`/`ProcessName`/`StartTime` を再検証するようにした。再検証に失敗した場合は
   停止せずマーカーのみ削除して安全側に倒す（`Skipped-Unverified`）。再検証を通過した場合のみ
   `Stop-Process -InputObject $process`（`-Id` による PID の再解決はしない）で停止し、終了確認は
   `Process.WaitForExit(5000)` を使う（PID の再検索ではない）。再検証・停止・待機のいずれかで
   例外が出た場合は停止しない側（＝マーカーも消さず、そのまま `throw`）に倒す。
   このパスをレビュー指摘どおり忠実にコード化したが、実際に「照合〜停止の間に本物の PID 再利用が
   発生する」競合状態を安全に再現するテストは書いていない（下記「対応した should-fix」節および
   「テストで意図的に省略したこと」を参照。生きた孤児 EXCEL の実停止テスト自体がタスクカード上
   任意とされていることに加え、極小の競合ウィンドウを確定的に再現する手段がないため）。

### round 1 レビューの should-fix 2件への対応

3. **[should-fix] 旧1行マーカーは安全だが完全な後方互換ではなく、直接テストもない** —
   **対応した（コードは全面対応、テストは可能な範囲で対応）。**
   `$recordedStartTicks` が読めない（2 行目がない旧形式）場合を、開始時刻が「不一致」の場合と
   区別した。旧形式マーカーが生きた `EXCEL.EXE` を指している場合は `Skipped-UnverifiedLegacy` を
   返し、**マーカーを削除しない**（将来の回収の手がかりを残す。レビュー推奨どおり）。
   旧形式マーカーが死亡 PID／非 Excel プロセスを指す場合は、2 行形式と同じくマーカーを削除してよい
   （回収すべき生存 Excel が存在しないため）。テストは `tests/Clear-XlsOrphans.Tests.ps1` の
   `Context 'legacy (1-line, PID-only) markers'` に、死亡 PID と非 Excel プロセスの 2 ケースを
   追加した。「旧形式マーカーが生きた EXCEL.EXE を指す」ケースだけは意図的にテストしていない。
   理由: これを安全に構築するには、`Invoke-XlsSession` を経由しない「素の」`EXCEL.EXE`
   （マーカーの排他リースを一切持たない生存プロセス）が必要だが、そのようなプロセスを作るには
   内部ヘルパー `Start-XlsApplication` を `Invoke-XlsSession` の外・テストコードから直接呼ぶ
   必要があり、G-06（COM は `Invoke-XlsSession` の中だけ、テストコードも同様。T-02 の例外は
   「`Invoke-XlsSession` がまだ存在しなかった」当時限定の読み替えであり、T-03 以降は厳格適用）に
   反する。実際に安全に再現しようとすると「ホストプロセスだけを強制終了し、子の `EXCEL.EXE` は
   生かしたままマーカーの排他リースだけを解放させる」という、単体テストの範囲を超えた踏み込んだ
   再現が必要になる。分岐ロジック自体は 2 ケース（`Skipped-DeadPid`/`Skipped-NotExcel`）と全く
   同じコードパスを通っており、コードレビューで確認できる状態にしてある。
4. **[should-fix] マーカー削除失敗を成功として報告する** — **対応した。**
   内部ヘルパー `Remove-XlsOrphanMarker` を新設し、`Remove-Item` の後に `Test-Path` で削除できた
   ことを確認、まだ残っていれば次の一手が分かる例外（`Marker '...' could not be removed. Check
   file permissions or whether another process still holds an exclusive lease on it.`）を投げる
   ようにした（レビュー提示のスニペットどおり）。マーカーを削除するすべての箇所
   （`Skipped-InvalidMarker`／`Skipped-DeadPid`／`Skipped-NotExcel`／`Skipped-Unverified`／
   `Stopped`）でこのヘルパーを使う。`Skipped-UnverifiedLegacy`／`Skipped-ActiveSession`／
   `Skipped-CannotAccess` はそもそもマーカーを削除しないためこのヘルパーを呼ばない。

### round 2 で見送ったテスト（round 1 で書いていたが構築できなくなったもの）

round 1 の実装メモにあった 2 テスト（「生きた EXCEL のマーカー開始時刻を書き換えて
`Skipped-Unverified` を確認する」「`-WhatIf` で `WhatIf-WouldStop` になることを確認する」）は、
どちらも「進行中セッションのマーカーの中身をテストコードから直接書き換える／読む」ことに依存して
いたが、round 2 の排他リース導入によりそれ自体ができなくなった（排他違反になる）ため削除した。
これは仕様の後退ではなく、まさにレビュー指摘 1. が求めていた「進行中セッションのマーカーには
一切手を出せない」という安全性そのものである。削除した2テストは、上記の新規テスト
（`Skipped-ActiveSession` 系 2 本）に置き換わっている。

### 設計上の既知の限界（round 1 で記載していたが、round 2 の排他リース導入で解消）

round 1 では「`Clear-XlsOrphans` を進行中の `Invoke-XlsSession` セッションと同時に呼ぶと、
稼働中のセッションを誤って停止しうる」ことをスコープ外の既知の限界として記録していたが、
round 1 レビューの blocking 指摘 1. により、これはスコープ外にできる話ではなく修正が必要な
契約違反だと判断された。round 2 でマーカーの排他リースを導入したことでこの限界は解消済み
（進行中セッションのマーカーは排他オープンに失敗するため、`Skipped-ActiveSession` として
一切変更されない）。
