# T-12 Test-XlsFormulas.ps1 CLI

## 目的
recalc.py 相当の CLI `skill/scripts/Test-XlsFormulas.ps1` を実装する(P4 完結)。

> 01-design.md §3.6:
> ```
> pwsh -File Test-XlsFormulas.ps1 <path> [timeoutSec=30] [-Force]
> ```
> - 出力: recalc.py 完全互換 JSON(標準出力へ)。
> - 終了コード: `error` キー(Excel 起動失敗・ファイル不在・タイムアウト)のときのみ非 0。`errors_found` / `refused` は 0(G-04)。
> - タイムアウト: `CalculateFullRebuild` を Runspace で走らせて timeoutSec で打ち切り、`{ "error": "timeout" }`。

## 仕様の具体化(実装判断は実装メモに記録)
- 環境注記: この開発機には pwsh(PowerShell 7)が無い。CLI は Windows PowerShell 5.1 の `powershell -File` でも pwsh でも動くこと(G-11 準拠なら自然に満たされる)。テストは powershell.exe で行う。
- 引数: 位置引数 `<path>`、位置引数 `[timeoutSec]`(既定 30)、スイッチ `-Force`。
- スクリプトは XlsAgent.psm1 を相対パスで Import し、Test-XlsFormulas を呼んで JSON を stdout へ 1 個だけ出力する。
- タイムアウト実装: 検証全体(Invoke-XlsSession 含む)を別 Runspace(STA necessity に注意 — Invoke-XlsSession は STA 必須。Runspace の ApartmentState を STA に設定)で実行し、timeoutSec 超過で打ち切り `{ "error": "timeout" }` を出力して非 0 終了。打ち切り時の Excel プロセスは PID マーカー+リースが残るので Clear-XlsOrphans で回収する(実装判断: CLI が自動で回収を試みるか、メッセージで案内するか — 安全性を優先し判断を記録)。
- error 系 JSON: `{ "error": "<説明>" }`(recalc.py 互換。ファイル不在・Excel 起動失敗・タイムアウト等)。exit 1。
- success / errors_found / refused: exit 0。
- stdout には JSON のみ(それ以外のログは stderr か抑制。エージェントがパースする前提)。

### 仕様の具体化(実装判断)
- **引数**: 位置引数 `<path>`(Position 0, Mandatory)、位置引数 `[timeoutSec]`(Position 1, 既定
  30)、スイッチ `-Force`。`param()` ブロックのバインディングをそのまま使い、順序を問わず
  `-Force` を混ぜられる(`script.ps1 path 30 -Force` でも `script.ps1 path -Force 30` でも可)。
  必須引数省略などの「CLI 使用法エラー」は PowerShell 標準のパラメーターバインディングエラーに
  任せ、`{ "error": ... }` の対象にはしていない(タスクカードが明示するエラー種別はファイル不在・
  Excel 起動失敗・タイムアウトの 3 つで、引数エラーはその範囲外と判断)。
- **タイムアウトの実装**: `RunspaceFactory.CreateRunspace` で STA の Runspace を作り(`ApartmentState
  = STA`、`ThreadOptions = ReuseThread`— COM オブジェクトはアパートメントに紐付くため同一スレッドを
  使い続ける必要がある)、その上で `PowerShell.AddScript({...}).BeginInvoke()` により
  `Import-Module XlsAgent.psm1; Test-XlsFormulas -Path ... -Force:... -AsJson` を非同期実行する。
  `AsyncResult.AsyncWaitHandle.WaitOne(timeoutSec * 1000)` で待ち、時間内に完了しなければ
  `PowerShell.BeginStop()` を投げっぱなしで呼んだ上で(完了を待たない)、即座に `{ "error": "timeout"
  }` を出力してプロセスを終了する。
- **プロセス終了は `TerminateProcess`(kernel32.dll の P/Invoke)を使う**(重要な実装判断、下記
  「踏んだ罠」参照)。`[Environment]::Exit()` では不十分だったことを実機で確認したための変更。
- **stdout への出力**は必ず `[Console]::Out.WriteLine(...)` で直接書く(`Write-Output`/パイプライン
  出力の既定フォーマッタを経由しない)。「stdout に JSON を 1 個だけ」という契約を、非対話ホストでの
  コンソール幅推定による意図しない改行混入のリスクなしに守るため。
- **exit code**: JSON に `error` キーがあるときだけ非 0。`Test-XlsFormulas -AsJson` が返す JSON は
  常に `status` キー(success/errors_found/refused)を持つ形なので、CLI 側は「パイプラインが例外なく
  完了したか」だけで正常系/異常系を判定する(例外時は `$ps.Streams.Error[0]` からメッセージを取り、
  `{ "error": "<メッセージ>" }` にする)。
- **`XlsAgent.psm1` が見つからない場合**もエラー JSON を返す(Excel を起動する前に
  `Test-Path -PathType Leaf` で確認)。タスクカードの「ファイル不在・Excel 起動失敗」の想定には
  ないケースだが、S-04(次の一手が分かるエラー)の精神で JSON 契約を保ったまま失敗させた。

### 踏んだ COM/CLR の罠(実機確認)
1. **`PowerShell.EndInvoke()` が投げる例外は PowerShell 側で `MethodInvocationException` に
   ラップされる**: `$ps.EndInvoke($asyncResult)` を直接メソッド呼び出しとして書くと、
   パイプライン内で発生した本来の例外(例: `Invoke-XlsSession` の `"File not found: '...'"`
   )が `Exception calling "EndInvoke" with "1" argument(s): "File not found: ...".` という
   ラップされたメッセージになることを実機で確認した。次の一手が分かる本来のメッセージ(S-04)を
   保つため、`$_.Exception.InnerException.Message` があればそちらを優先して使うようにした。
2. **【重要】`[Environment]::Exit()` は、COM 呼び出しでブロック中の別スレッド(今回は STA
   Runspace のパイプライン実行スレッド)が生きていると、想定よりずっと長く実際のプロセス終了を
   遅延させることを実機で確認した**。最初は `[Environment]::Exit()` で実装したが、
   `timeoutSec=1` でタイムアウトさせたテストで:
   - CLI プロセス自体の壁時計時間が 1 秒ではなく 3.6 秒以上かかった(`[Environment]::Exit()`
     呼び出し後もプロセスが即座には終わっていない)。
   - さらに悪いことに、裏で `Invoke-XlsSession` の `finally`(Close→Quit→Release→GC×2→マーカー
     削除)がそのまま完走してしまい、`Clear-XlsOrphans` が回収すべきマーカーが既に消えている
     (＝正規の孤児回収経路が機能しない)状態を繰り返し観測した。
   Win32 API `TerminateProcess`(`kernel32.dll`、P/Invoke で `XlsAgentCli.NativeMethods` として
   宣言。`XlsAgent.psm1` の `NativeMethods` とは別名前空間にして衝突を避けた)に切り替えたところ、
   `timeoutSec` にほぼ一致する壁時計時間(例: `timeoutSec=2` で実測 2498ms)でプロセスが確実に
   終了することを確認した。すべての終了経路(success/errors_found/refused/error/timeout)で
   一貫して `TerminateProcess` を使う(先に `[Console]::Out.Flush()` を呼んでから終了するので
   正常系でも出力が欠けない)。
3. **【重要】`TerminateProcess` で確実にプロセスが即座に終了するようになった結果、
   `Start-XlsApplication`(Excel.Application の COM アクティブ化)が完了する前にタイムアウトが
   発生すると、そのセッションの `Invoke-XlsSession` マーカーファイルはそもそも一度も書き込まれない
   ことを実機で確認した**。マーカーは `Start-XlsApplication` が返った**後**に書き込まれるため
   (`Invoke-XlsSession` の設計どおり)、それより前にプロセスが強制終了されれば当然マーカーは
   存在しない。この状態の EXCEL.EXE は `Clear-XlsOrphans` の設計上(G-10: マーカーのない PID には
   絶対に触れない)回収できない。この開発機では `New-Object -ComObject Excel.Application` の所要
   時間に非常に大きな幅があることを実機で確認した(同条件で 3.8 秒・6.5 秒・61.2 秒、という
   ケースを観測。61 秒台という値が 2 回連続で再現しており、既定の DCOM アクティブ化タイムアウト
   付近の値に見える。原因はこの開発機固有の環境要因〈DCOM/レジストリ状態や常駐ソフトとの競合〉と
   推測されるが特定はできていない。T-01〜T-11 で観測されていない値だが、当時と同じ
   `Start-XlsApplication`/`New-Object -ComObject Excel.Application` を変更なく呼んでいるだけなので
   T-12 固有の不具合ではないと判断した)。このため CLI 自体は「タイムアウト後、マーカーがあれば
   `Clear-XlsOrphans` で回収できるが、マーカーが一度も書かれていなければ CLI からは回収不能」を
   受け入れる設計にした(CLI は `Clear-XlsOrphans` を自分から呼ばない。呼び出し元がテストや
   エージェントの責務として回収する。詳細は CLI 本体の `.NOTES` 参照)。
   **SKILL.md gotchas 候補**: `Test-XlsFormulas.ps1 <path> <timeoutSec>` を短い `timeoutSec`
   で呼ぶと、Excel の COM アクティブ化そのものが完了する前に打ち切られることがあり、その場合は
   マーカーの残らない(＝ `Clear-XlsOrphans` で追跡できない)EXCEL.EXE が残る可能性がある。
   `timeoutSec` は「検証したい重さ」に対して十分な余裕を持たせるべきで、極端に短い値
   (例: 1 秒)は「本当にタイムアウトの入口(Excel 起動)で打ち切られただけ」なのか「検証内容が
   重くて打ち切られた」のかを区別できない。
4. **Get-ExcelPids(`tests/Common.ps1`)をパイプラインへ直接つなぐと `,@(...)` の単項カンマ包みが
   1 段しか外れず、個々の PID ではなく配列全体が 1 個の要素として流れる**(実機確認、テスト実装中に
   踏んだ罠)。`Get-ExcelPids | Where-Object { ... -notcontains $_ }` と書くと `$_` が「PID の配列
   そのもの」になり、意図したフィルタにならない(ヒット 0 件のときは `Get-Process -Id <空配列>` が
   `ParameterBindingValidationException` で落ちるところまで実機で確認した)。`Assert-NoOrphanExcel`
   自身が `$current = Get-ExcelPids` といったん変数に代入してから `Where-Object` へ渡している
   のと同じパターンに合わせ、`TestXlsFormulasCli.Tests.ps1` 側も必ず変数へ代入してから
   フィルタするように修正した。**SKILL.md gotchas 候補**: `Get-ExcelPids` に限らず、
   `return ,@(...)` で包んだ関数の戻り値はパイプへ直接つながず、いったん変数に代入してから
   フィルタ/列挙すること。

### タイムアウト後の EXCEL.EXE 回収方針(タスクカードが明示した実装判断)
CLI プロセス自身は `Clear-XlsOrphans` を呼ばない。理由: `Invoke-XlsSession` のマーカーは
`FileShare.None` の排他リースとして、まだ生きている可能性のある別スレッドが保持し続けているため、
CLI プロセスが生きている間に `Clear-XlsOrphans` を呼んでも必ず `Skipped-ActiveSession` になり
安全に何もできない(G-10 の「進行中セッションには触れない」という設計そのもの)。CLI プロセスが
`TerminateProcess` で終了すれば OS が全ハンドル(マーカーの排他リースを含む)を即座に解放するため、
その後に**別プロセスから** `Clear-XlsOrphans` を呼べば、マーカーが書き込まれていた場合に限り
真の孤児として検出・回収できる。呼び出し元(テスト・エージェント)の責務とした。
`tests/TestXlsFormulasCli.Tests.ps1` のタイムアウトテストはこの方針に沿って: (a) まず
`Clear-XlsOrphans` を正規の回収経路としてポーリング呼び出しし、(b) それでも残る PID は
「本テスト実行前のベースラインになかった」ことで自テスト起動と確認できるものに限り個別に
`Stop-Process -Id <PID> -Force` する(`tests/Clear-XlsOrphans.Tests.ps1` が自ら起動したダミー
プロセスの後始末に使うのと同じ「既知の特定 PID だけを個別に止める」パターン。
`Get-Process EXCEL | Stop-Process` のような全殺しはしていない。G-10)。

## round 1 レビュー対応(G-16、harness/state/reviews/T-12.md、判定 fix: blocking 2 件・should-fix 2 件・nit 1 件)

### 1. [blocking] マーカー作成前のタイムアウトで安全に回収不能な EXCEL.EXE が残る → 対応した

指摘のとおり、旧実装はタイマーを CLI 起動直後(Excel を起動する前)から測っていたため、
`Start-XlsApplication`(Excel.Application の COM アクティブ化。この開発機では実測 4〜61 秒の幅を
確認)が timeoutSec を超えると、`Invoke-XlsSession` がマーカーを書き込む前に `TerminateProcess`
してしまい、`Clear-XlsOrphans`(G-10 によりマーカーのない PID には絶対に触れない)では永久に
回収できない EXCEL.EXE が残り得た。

対応: レビューが許可した「同一プロセス内でも所有権確立イベントを待ってからタイマー開始でよい」
方式を採用した(親子プロセス分離まではしていない。理由は後述)。`skill/scripts/Test-XlsFormulas.ps1`
に「フェーズ 1: 所有権確立待ち」を追加した:
- CLI 起動時に `$env:TEMP\xlsagent` の既存マーカー名を記録しておく。
- パイプラインを `BeginInvoke` した直後、**新しいマーカーファイルが現れるか、パイプラインが
  （Excel 起動失敗などでマーカーを一度も書かずに）自然完了するまで無期限に待つ**（100ms 間隔で
  ポーリング）。この区間では `TerminateProcess` を一切呼ばない(強制終了しない)。
- 新しいマーカーが現れて初めて「フェーズ 2」として `timeoutSec` 秒の `AsyncWaitHandle.WaitOne`
  を開始する。ここで打ち切られた場合のみ `TerminateProcess` を呼ぶ。この時点ではマーカーの存在が
  保証されているため、`Clear-XlsOrphans` が後から安全に回収できる。

親子プロセス分離(レビューの構成図のフル版)は採用しなかった: レビュー本文が「即時終了が必要なら」
という条件付きで提示しており、「所有権確立前に強制終了しない」という安全上の必須要件は
同一プロセス内の実装でも満たせるため。CLI の起動オーバーヘッド・実装量・レビュー観点を増やす
親子プロセス化は今回のタスクカードの範囲(CLI 1 本の実装)に対して過大と判断した。

決定的な検証: `tests/TestXlsFormulasCli.Tests.ps1` に実 Excel を使わないフェイクモジュール
(`New-XlsCliFakeSlowModule`/`New-XlsCliFakeFailingModule`)による Context
`'timeout mechanism (deterministic, no real Excel; round 1 review should-fix)'` を追加し、
「所有権確立後に timeoutSec ちょうどで打ち切られる」「所有権確立前にパイプラインが失敗すると
timeoutSec を待たずに error JSON になる」の両方を実 Excel の起動時間に依存せず固定した。実 Excel
での検証は Context `'timeout with real Excel (post-ownership, ...)'` の 1 本(下記 2. 参照)。

### 2. [blocking] ベースライン差分だけで Excel を直接停止している → 対応した

指摘のとおり、`tests/TestXlsFormulasCli.Tests.ps1` のタイムアウトテストの後始末が
「ベースラインになかった PID を直接 `Stop-Process`」していたのは、`XlsAgent.psm1` の

**対応方針の検討**: レビューの修正案(runToken を親からワーカーへ渡し、マーカー内容の書き込みと

`XlsAgent.psm1` に触れない代替案」を検討した。具体的には、COM 経由で起動された EXCEL.EXE の
親プロセス ID(PPID)を使って所有権を相関できないか実機で確認した:

```powershell
$app = New-Object -ComObject Excel.Application
Get-CimInstance Win32_Process -Filter "Name='EXCEL.EXE'" | Select ProcessId, ParentProcessId
# ProcessId=21144, ParentProcessId=1896 (svchost.exe、DCOM Launcher) であり、
# 呼び出し元 PowerShell プロセス(PID 20548)とは一致しないことを実機で確認した。
```
COM のローカルアクティブ化は DCOM Launcher サービス(`svchost.exe`)経由でプロセスが起動されるため、
PPID は常に `svchost.exe` になり、呼び出し元プロセスとは相関しない。この経路は使えないことを
実機で確定させた。

このため、レビューが「公開 API を変えない範囲で」と明示的に許容している
「`Invoke-XlsSession` への内部向け通知フックの追加」を採用した。ただし `runToken` を
`Invoke-XlsSession` の新しい**パラメーター**として追加すると、T-03 の公開シグネチャ変更になり
G-14(隣の関数に手を出さない)・G-01 の精神に反する。代わりに、**`$env:XLSAGENT_RUN_TOKEN` という
非公開の環境変数フック**にした:
- 環境変数が未設定なら `Invoke-XlsSession` の動作は一切変わらない(既存のシグネチャ・既定動作を
  完全に維持。`Invoke-XlsSession.Tests.ps1` の全 11 テストが無改造のまま緑であることで確認済み)。
- 環境変数が設定されているときだけ、マーカー本体の `Write`+`Flush` が完了した**直後**に、
  ロックしない別ファイル `$env:TEMP\xlsagent-ready\<runToken>.ready`(PID・開始時刻・runToken の

## round 3 レビュー対応(G-16、harness/state/reviews/T-12-r3.md、判定 fix: blocking 1 件・should-fix 1 件・nit 1 件)

### 1. [blocking] StartTicks を解析するだけで実プロセスと照合していない → 対応した

指摘のとおり、round 2 版の `Test-XlsCliOwnershipReady` は ready ファイルの StartTicks を
`[long]::TryParse` するだけで、`Get-Process` が返す実プロセスの
`StartTime.ToUniversalTime().Ticks` と突き合わせていなかった。これでは「たまたま同じ PID の
何らかのプロセスが生きているだけ」でも所有権確立と誤認しうり、PID 再利用への耐性が未達だった。

対応: レビューのスニペットどおり `skill/scripts/Test-XlsFormulas.ps1` の
`Test-XlsCliOwnershipReady` を修正した。
- `$readyStartTicks -le 0` も無効値として弾くようにした。
- `Get-Process` で取得したプロセスを `$proc.Refresh()` した上で、`$proc.HasExited` が真、
  または `$proc.StartTime.ToUniversalTime().Ticks` が ready ファイルの値と一致しない場合は
  `$null` を返す（＝未確立のまま）ようにした。`Clear-XlsOrphans` が孤児回収時に行っている
  PID+開始時刻の完全一致照合と同じ考え方。

テスト追加: `tests/TestXlsFormulasCli.Tests.ps1` の `New-XlsCliFakeReadyModule` に
`-WrongStartTicksFirst` を追加した。正しい PID・runToken だが固定の誤った StartTicks
（`123456789`）で ready ファイルを最初に書き、`PreReadyDelaySeconds`（3 秒）後に実プロセスの
正しい StartTicks で上書きする。新規 It
`'does not accept a ready file until its StartTicks matches the live process (round 3 review
blocking: PID-reuse resistance)'` で、`timeoutSec=1` に対して合計経過時間が 3.4 秒を超える
（＝誤った ready を最初のポーリングで受理せず、正しい ready まで待ってから 1 秒を測った）ことを

約 1〜1.5 秒で打ち切られていたはずである(手動プローブで実機確認: 修正後は 4679ms で正しく
タイムアウトすることを確認)。

  `Test-Path` で存在しないこと（＝削除されたこと）を明示的に検証するようにした（対象プロセスは
  フェイクモジュール自身の PID で、CLI 終了後は既に存在しないので `Skipped-DeadPid` になる）。
- 実 Excel の timeout テストにも、CLI 終了直後（最初の `Clear-XlsOrphans` 呼び出しより前）の
  時点で新規マーカーが実在したかを記録する `$sawNewMarkerAtStart` を追加し、実在した場合に限り
  `$clearResultsSeen` に `Stopped`／`Skipped-DeadPid`／`Skipped-UnverifiedLegacy`／
  `Skipped-Unverified`／`Skipped-NotExcel`／`Skipped-InvalidMarker` のいずれかが最低 1 件
  含まれることを検証するようにした（実装メモの「BeginStop() が競合に勝ってマーカーが最初から
  存在しないケース」ではこの検証をスキップする。安全に判定できないものを無理に検証しない）。

### 3. [nit] timeout ごとに ready ファイルが残る → 対応した

指摘のとおり、内側の finally は `$timedOut` のときだけ ready ファイルの削除をスキップしていたが、
この finally は `Complete-XlsCli`（`TerminateProcess` を含む）より**前**に必ず実行されるため、
削除を `$timedOut` で条件分岐する必要はなかった。`Remove-Item -LiteralPath $readyPath` を
無条件（ベストエフォート）に変更した。上記の Action 検証テストに、タイムアウト後に新規の
`.ready` ファイルが残っていないことを確認するアサーションも追加した。
