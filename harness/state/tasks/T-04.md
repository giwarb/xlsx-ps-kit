# T-04 Save-XlsWorkbook

## 目的
保存の唯一の経路 `Save-XlsWorkbook` を実装する(G-09: 保存はこの関数のみ)。

> 01-design.md §3.2:
> ```
> Save-XlsWorkbook -Workbook <obj> -Path <string>
> ```
> - 拡張子から `FileFormat` を決定: `.xlsx`→51, `.xlsm`→52, `.xltx`→54, `.xltm`→53, `.csv`→6。
> - 保存前に `Calculation=xlCalculationAutomatic` に戻し `CalculateFullRebuild` を実行(手動のまま保存すると開いた人の環境で古い値が見える)。
> - 上書き時は `DisplayAlerts=$false` 前提で `SaveAs`。既存パスと同一なら `Save`。

## 実装メモ(Sonnet が記入)

### 環境について
今回の実装環境では実 Excel（Microsoft Office）が動作し、`Invoke-Pester` を実際に自分で実行して
緑を確認できた（T-03 のレビューではサンドボックス制約により実行できなかった旨が記録されている）。
以下の確認事項はすべて本セッションで実機実行して得たもの。

### 実装した関数
- `Get-XlsSaveFileFormat -Path <string>`（内部ヘルパー、非公開）: 拡張子 → FileFormat の純粋関数（COM なし）。
- `Test-XlsSamePath -PathA <string> -PathB <string>`（内部ヘルパー、非公開）: `[IO.FileInfo].FullName` を
  `OrdinalIgnoreCase` で比較する純粋関数（COM なし）。Save-XlsWorkbook 側で `$Workbook.Path`/`$Workbook.FullName`
  を読んで文字列化してから渡す形にし、COM プロパティ読み取りとパス比較ロジックを分離した。これにより
  パス比較ロジックだけを COM なしで単体テストできる（G-06 を保ったまま単体テスト可能性を確保）。
- `Set-XlsCalculationAutomatic -Application <obj>`(内部ヘルパー、非公開): `Application.Calculation` を
  Automatic に戻し `CalculateFullRebuild()` を呼ぶ。T-10 の Test-XlsFormulas と共有する想定（タスクカード指示どおり切り出した）。
- `Save-XlsWorkbook -Workbook <obj> -Path <string>`: 上記ヘルパーを組み合わせて実装。
  同一パス判定は `Test-XlsSamePath -PathA $Workbook.FullName -PathB $Path`（`$Workbook.Path` が
  空文字列＝未保存workbookの場合は PathA を渡さず必ず SaveAs 側に倒す）。

### 踏んだ COM の罠(実機確認)
1. **Application.Calculation は保存の瞬間の値が xl/workbook.xml の `<calcPr calcMode="...">` に焼き込まれる**。
   Manual のまま SaveAs すると `calcMode="manual"` が明示され、Automatic で SaveAs すると `calcMode` 属性自体が
   省略される(Excel の既定値が automatic のため)。これを ZIP として直接開いて確認した(下記「(b) の検証方法」参照)。
2. **`.xltx`/`.xltm` は `Workbooks.Open` で開き直すと、テンプレート自体を編集用に開くのではなく、
   それを元にした新規ブック(未保存、`FileFormat` は既定の 51 など)が生成される**。Excel のテンプレート
   ダブルクリック相当の挙動が `Workbooks.Open` でも起きる。そのため、テンプレート形式の `FileFormat` を
   確認するテストは reopen ではなく「SaveAs 直後、閉じる前にその場で `Workbook.FileFormat` を見る」形にした。
3. **`Workbook.HasVBProject` は Trust Center の「VBA プロジェクト オブジェクト モデルへのアクセスを信頼する」
   設定なしでも例外を投げずに読める**(実機確認、`False` が返る)。例外を投げるのは `Workbook.VBProject`
   オブジェクト自体へのアクセスであり、`HasVBProject` は単なる bool プロパティなので影響を受けない。
4. **`Workbook.Save()` は `DisplayAlerts=$false` の下で確認ダイアログなしに即座に完了する**(同一パス・同一
   形式での上書き)。`SaveAs` を「既に自分自身が開いているファイルと同じパス」に対して呼んでもロック競合や
   例外にはならない(同一プロセスが保持しているロックのため)。このため「Save 経路が実際に選ばれたか」を
   外部から観測できる副作用の差はほぼ無く、テストでは `Test-XlsSamePath` の判定ロジック自体を COM なしで
   単体テストする形で担保した(上記「実装した関数」参照)。
5. **Manual のまま先行セルの値を書き換えても、数式セルの `Value2` は古いまま**(実機確認: `=A1*2` で
   `A1` を 10→99 に変えても `A2` は 20 のまま)。`Set-XlsCalculationAutomatic` の
   `Calculation=Automatic; CalculateFullRebuild()` で確実に最新化されることを確認した(99*2=198)。

### (b) の受け入れ要点「保存後に開き直すと Calculation が Automatic」の検証方法について(判断の記録)
設計(01-design.md §3.2)は保存**後**の `Application.Calculation`(ライブセッション側)の扱いを明記していない。
一方で T-03 で確立した `Invoke-XlsSession` は、`Workbooks.Open`/`Add` の直後・`ScriptBlock` 実行前に必ず
`Application.Calculation = xlCalculationManual` を強制する(G-06 上、COM は `Invoke-XlsSession` 経由でしか
触れないため、この強制を回避してファイル側の状態を COM で覗く手段がない)。

そこで次の 2 点を切り分けて判断した。
- **ファイルに焼き込まれる状態**(受け入れ要点(b)が指しているもの): 「踏んだ罠 1」のとおり、保存の瞬間の
  `Application.Calculation` がそのまま `xl/workbook.xml` に反映される。`Save-XlsWorkbook` は保存前に必ず
  Automatic + `CalculateFullRebuild` を行うため、保存された瞬間に(b)は満たされる。これを COM を使わず
  `System.IO.Compression.ZipFile` で `xl/workbook.xml` を直接読んで検証した(`tests/Save-XlsWorkbook.Tests.ps1`
  の `Get-XlsxCalcModeFromDisk`)。COM を経由しないので G-06 に抵触しない。
- **保存後のライブセッション側の `Application.Calculation`**: 上記の理由で(b)は保存の瞬間に確定しており、
  ライブセッション側をどちらに戻しても(b)の充足には影響しない。`Invoke-XlsSession` がセッション全体を通じて
  「Manual で始まる」という前提を確立している以上、`Save-XlsWorkbook` から戻った後の `ScriptBlock` の残りの
  処理(続けて別のセルを編集する等)が引き続き Manual の恩恵(パフォーマンス)を受けられるよう、保存後は
  **Manual に戻す**実装にした。`finally` ブロックで戻すため、`Save`/`SaveAs` が例外を投げた場合でも
  Manual に戻ることを保証している。

### .xlsm の HasVBProject 検証(タスクカードの2段構え方針への対応)
1段目(必須): マクロなしの新規ワークブックを `.xlsm` として `Save-XlsWorkbook` で保存し、`FileFormat` が 52、
`HasVBProject` が `false` のまま拡張子と形式が一致することを検証した。実機で確認済み(緑)。

2段目(既存 `.xlsm` があれば `HasVBProject` 維持を検証): リポジトリにマクロ付き `.xlsm` fixture が存在しない
ため実施しなかった。マクロ付き `.xlsm` を新規に用意するには Excel の Trust Center 設定
(「VBA プロジェクト オブジェクト モデルへのアクセスを信頼する」)を有効化する必要があるが、これは
実行環境のセキュリティ設定を書き換える操作であり、本タスクの範囲外・かつ避けるべき操作と判断し、行わなかった。
将来 T-13/T-16 等でマクロ付き fixture が正当な理由で追加された場合は、その fixture を使って2段目を
追加できる(`Save-XlsWorkbook` 自体の実装は変更不要。フォーマット選択とファイル保存の経路は拡張子だけで
決まり、マクロの有無を関知しないため)。

### レビュー指摘への対応
初回実装のため該当なし(前提タスク T-03 のレビュー指摘は「テストの COM は Invoke-XlsSession 内のみ／
保存は Save-XlsWorkbook のみ／fixture は静的ファイル／定数は `$script:Xl` 集約+`com-constants.md` 追記」
であり、いずれも本タスクの実装・テストで踏襲した: テストの COM 操作はすべて `Invoke-XlsSession` の
`ScriptBlock` 内。保存を伴う準備は行わず、既存の `tests/fixtures/blank.xlsx` は使用していない(すべて
`New-TempXlsPathWithExtension` で新規パスを都度発行し、`Invoke-XlsSession` の中で作成・保存する)。
使用した定数はすべて `$script:Xl` に集約し `com-constants.md` に実測日付・確認方法つきで追記した)。

### 回帰修正(範囲内の必要な変更)
`tests/T01.Tests.ps1` の「スタブ関数は throw 文を含む」ループから `Invoke-XlsSession` と
`Save-XlsWorkbook` を除外した。`Save-XlsWorkbook` は自身の `ScriptBlock` 直下に `throw` を持たず
(拡張子検証は `Get-XlsSaveFileFormat` に、パス比較は `Test-XlsSamePath` に委譲しているため)、実装後は
このテストが確実に失敗する。T-03 round 1 レビューで「T-01 の定数件数 assertion が次タスクで陳腐化する」
と指摘されたのと同じ性質の回帰であり、同じ考え方(タスクカードの範囲外を触っていないというより、
自分のタスクの実装が引き起こす必要な回帰修正)で対応した。`Invoke-XlsSession` は実装後も自身のエラー処理に
`throw` が残っているため偶然パスしていたが、もはやスタブではない事実を明示するため合わせて除外した。

## レビュー round 1 (harness/state/reviews/T-04.md) への対応 (G-16)

判定: `fix`。指摘ごとに対応した/対応しない(理由)を記録する。

### 1. [blocking] 単一セルへの scalar `Value2` 代入も G-08 違反 → 対応した
指摘のとおり、G-08「Range.Value2 への代入は [object[,]] のみ」に単一セルの例外はなく、
`tests/Save-XlsWorkbook.Tests.ps1` の5箇所(`$marker`、`'first'`、`'second'`、`10`、`99`)は
scalar を直接代入していた。自己チェックの○も事実と一致していなかった(訂正: 誤り)。

対応: レビュー指摘のスニペットに沿って `[Array]::CreateInstance([object], 1, 1)` で 1x1 の
`[object[,]]` を作るヘルパー関数 `New-XlsSingleCellArray -Value <obj>` をテストファイルに追加し、
該当5箇所すべてをこのヘルパー経由の代入に置き換えた(`tests/Save-XlsWorkbook.Tests.ps1`)。
`$ws.Range('A2').Formula = '=A1*2'` は `Formula` プロパティであり `Value2` ではないため G-08 の
対象外(変更していない)。

### 2. [should-fix] Automatic 切替〜Save/SaveAs〜状態復元を同じ try/finally に入れる → 対応した
指摘のとおり、`Set-XlsCalculationAutomatic` の呼び出しとパス判定(`$Workbook.Path`/`FullName` の
COM プロパティ読み取りを含む)が `try` の外にあり、そこで例外が起きると Manual に戻らないまま
関数を抜ける可能性があった。また `Save`/`SaveAs` の失敗が生の COM `HRESULT` メッセージのまま
伝播し S-04 を満たしていなかった。

対応: レビュー指摘のスニペットに沿って `skill/scripts/XlsAgent.psm1` の `Save-XlsWorkbook` を
書き換えた。`$app = $Workbook.Application` を先に取っておき、`Set-XlsCalculationAutomatic` の
呼び出し・パス判定・`Save`/`SaveAs` をすべて1つの `try` に入れ、`catch` で
`"Failed to recalculate or save workbook to '$Path'. Check the parent directory, permissions, file locks, and extension. Excel reported: $($_.Exception.Message)"`
に包み直し、`finally` で `$app.Calculation = $script:Xl.xlCalculationManual` を保証するようにした。

検証テストを追加: `tests/Save-XlsWorkbook.Tests.ps1` の新 Context
「error handling when Save/SaveAs fails」に、存在しない親ディレクトリへ `SaveAs` させて
(1) ラップ後のメッセージに対象パスと `'parent directory'` という語が含まれること(次の一手が
分かる文であること)、(2) `catch` 後も `$app.Calculation` が Manual に戻っていること、の両方を
検証するテストを追加した。実機で SaveAs が生の COM エラー(「ファイル '...' にアクセスできません」
系)を投げることをあらかじめ手元で確認してから、期待するラップ後メッセージの形をテストに書いた。

### 3. [should-fix] OOXML テストの StreamReader にエンコーディングを明示 → 対応した
指摘のとおり、`tests/Save-XlsWorkbook.Tests.ps1` の `Get-XlsxCalcModeFromDisk` 内
`New-Object System.IO.StreamReader($stream)` はエンコーディングを明示しておらず、S-01/P-3
(ファイル I/O は `-Encoding UTF8` を明示)の趣旨に反していた(xl/workbook.xml は BOM なし UTF-8
なので実害はなかったが、規約違反は規約違反)。

対応: レビュー指摘のスニペットに沿って
`New-Object -TypeName System.IO.StreamReader -ArgumentList @($stream, [Text.Encoding]::UTF8, $true)`
に変更した。
