# T-03 Invoke-XlsSession

## 目的
COM セッション管理の中核 `Invoke-XlsSession` を実装する。以後すべての COM 操作はこの中でだけ行われる。

> 01-design.md §3.1:
> ```
> Invoke-XlsSession -Path <string> [-ReadOnly] [-Visible] -ScriptBlock { param($app, $wb) ... }
> ```
> - 新規 `Excel.Application` を起動(`GetActiveObject` 禁止)。
> - 初期状態: `Visible=$false, DisplayAlerts=$false, ScreenUpdating=$false, EnableEvents=$false, AskToUpdateLinks=$false, Calculation=xlCalculationManual`。
> - `Workbooks.Open($Path, UpdateLinks:=0, ReadOnly:=$ReadOnly)`。ファイル不在で `-ReadOnly` でなければ `Workbooks.Add()`。
> - 開いた直後に `$wb.ReadOnly` を確認し、`-ReadOnly` 指定なしで読み取り専用になった場合は例外(他プロセスが開いている)。
> - STA でなければ例外(`[Threading.Thread]::CurrentThread.ApartmentState`)。
> - 起動した PID を `$env:TEMP\xlsagent\<pid>.marker` に記録。
> - `finally` で `Workbook.Close(SaveChanges:=$false)`(保存は ScriptBlock 内で `Save-XlsWorkbook` を明示)、`Application.Quit`、`ReleaseComObject` を逆順、`[GC]::Collect(); [GC]::WaitForPendingFinalizers()` を 2 回、マーカー削除。
> - 戻り値: ScriptBlock の戻り値をそのまま返す。

### やったこと

- `skill/scripts/XlsAgent.psm1` の `Invoke-XlsSession` を本実装。T-02 の内部ヘルパー

  Application の起動・初期状態設定・Quit・Release・GC×2 は T-02 のものをそのまま呼ぶだけにした)。
- 実装順序:
  1. STA 検査(`[Threading.Thread]::CurrentThread.ApartmentState`)。Excel を起動する**前**に行い、
     MTA なら Excel を1つも起動せずに例外にする(無駄なプロセス起動を避ける)。
  2. `$env:TEMP\xlsagent` マーカーディレクトリを用意。

  4. 起動直後に `$env:TEMP\xlsagent\<pid>.marker` を書き込む(内容は PID そのもの、UTF-8)。
  5. `Test-Path -PathType Leaf` でファイル存在確認。存在すれば `Workbooks.Open($Path, 0, [bool]$ReadOnly)`
     (UpdateLinks:=0)。存在せず `-ReadOnly` も指定されていなければ `Workbooks.Add()`。存在せず
     `-ReadOnly` が指定されていた場合は、読むものが無いため即座に例外(設計に明記されていない
     組み合わせだが、次の一手が分かる文で throw する判断をした)。
  6. `$wb.ReadOnly` を確認し、`-ReadOnly` 指定なしで true なら「他プロセスが開いている可能性」を
     明示した例外。
  7. **ここで初めて** `$app.Calculation = $script:Xl.xlCalculationManual` を設定
     (T-02 実装メモの罠どおり、Workbooks.Open/Add の後・ScriptBlock 実行前。Codex 承認済みの順序)。
  8. `& $ScriptBlock $app $wb` を実行し、戻り値をそのまま `return`。
  9. `finally`: `$wb.Close($false)`(例外は握りつぶす)→ `ReleaseComObject($wb)` →
     `Stop-XlsApplication -Application $app`(内部で `Quit → ReleaseComObject($app) → GC×2`、
     T-02 でレビュー済みの実装をそのまま使用)→ マーカーファイル削除。
     `Close` の失敗が Release/Stop-XlsApplication/マーカー削除を妨げないよう、内側にもう一段
     `try/finally` を入れた。
- `$script:Xl` に今回実際に使った `xlCalculationManual = -4135` だけを追加した(T-01 の「空の器」
  テストはこの追加と衝突するため下記のとおり更新した)。`skill/reference/com-constants.md` の

  (a) 存在しないパス → `Workbooks.Add`(新規未保存ワークブックは `$wb.Path` が空文字列になることで判定)。

      `-ReadOnly` なしの `Invoke-XlsSession` が「read-only」を含む例外を投げる。

     (EXCEL.EXE が残らない)。
  (d) `ScriptBlock` の戻り値(GUID 文字列)がそのまま透過する。
  追加: STA 検査(MTA の `runspace` から呼び出すと Excel を1つも起動せずに例外)、

### 使った読み替え(G-06) — round 1 の判断は Codex レビューで却下、round 2 で撤回

round 1 では、タスクカード本文の「使った読み替えは実装メモに明記」という許容を、T-02 の
「`Invoke-XlsSession` 未実装期間のみの一時的な G-06 読み替え」にも適用できると解釈し、
テストファイルから `Start-XlsApplication`/`Stop-XlsApplication` を直接呼んでいた。
Codex レビュー(round 1、blocking)は、`tests/T02.Tests.ps1` 自身が「T-03 以降は厳格適用」と
明記している以上、`Invoke-XlsSession` が実装された T-03 ではこの読み替えは使えないと指摘し、
これは正当な指摘だと判断した(T-02 の読み替えは "まだ `Invoke-XlsSession` が無いから" という
理由に限定されたものであり、"内部ヘルパーが安全だから" は別の理由であって読み替えの正当化にならない)。
**round 2 でこの読み替えは撤回し、テストは COM を一切直接操作しない形に書き直した**
(`New-TestWorkbookFile` は公開関数 `Invoke-XlsSession` のみを使う、ロック保持は別 `runspace` 上で
公開関数 `Invoke-XlsSession` を呼び出しその `ScriptBlock` 内で同期オブジェクトにより保持する。
詳細は下記「レビュー指摘への対応」参照)。現時点でこのタスクに残っている G-06 上の読み替えはない。

### 踏んだ COM の罠(S-05)

1. **`.NET` の `PowerShell` ホスト API では、`try/catch` で捕まえた例外でも `PowerShell.HadErrors` が
   `$true` になることがある(`Streams.Error` は空のまま)。** STA 検査テストで、別 `runspace`
   (`ApartmentState = MTA`)上で `Invoke-XlsSession` を呼び、内側の `try/catch` で例外メッセージを
   文字列として返すようにしたところ、`$ps.Streams.Error.Count` は 0 なのに `$ps.HadErrors` は `$true`
   だった。これは `Invoke-XlsSession` の挙動ではなく、内部でエンジンが例外を記録する際の
   ホスト API 側の仕様(`$Error` 自動変数には捕捉済みでも1件追加される)によるもので、
   `HadErrors` をテストの合否判定に使うのは不適切と判断し、返ってきた文字列メッセージの内容
   (`'threw:'` と `'STA'` を含むか)だけで判定するようにテストを直した。
2. (再確認・利用)T-02 実装メモの罠どおり、`Application.Calculation` は `Workbooks.Count` が 0 の間は
   設定できない。`Invoke-XlsSession` では `Workbooks.Open`/`Add` の**直後**・`ScriptBlock` 実行**前**に
   設定することで解消した(設計 §3.1 の記述順とは異なるが、Codex レビューで承認済みの実行順序)。
3. **新規未保存ワークブック(`Workbooks.Add()` の戻り値)は `Workbook.Path` が空文字列になる。**
   `FullName` は仮の名前(`Book1` など)を含むため、「`Add` されたか `Open` されたか」を判定する
   受け入れテスト (a) には `Path` が空かどうかを使うのが安定していた(`FullName` は環境のロケールで
   既定名が変わりうるため避けた)。
4. `Workbooks.Open` の第 2・第 3 引数(`UpdateLinks`, `ReadOnly`)は位置引数で渡せば十分だった
   (設計ドキュメントの `UpdateLinks:=0, ReadOnly:=$ReadOnly` という表記は VBA 風の説明であり、
   PowerShell の COM 遅延バインディングでは名前付き引数構文は使えない/不要。位置引数のみで
   `Filename, UpdateLinks, ReadOnly` の順に渡せば意図どおりに動く)。
5. ファイルが存在せず、かつ `-ReadOnly` が指定された場合の挙動は設計・タスクカードに明記が無い
   組み合わせだった。「読むものが無いのに読み取り専用を要求している」矛盾した入力として、
   `Workbooks.Add()` にフォールバックせず即座に例外にする判断をした(次の一手が分かる文で、
   `-ReadOnly` を外すか、パスを確認するよう促す)。設計変更ではなく未規定部分の実装時判断
   (01-design.md §7 の「決めていないこと」の枠組みに準ずる)。

### T-01 テストとの衝突と対応

T-01 の `tests/T01.Tests.ps1` には「`$script:Xl` は空のまま(skeleton only)」というテストがあったが、
これは T-03 のタスクカード本文が明示的に指示する「使用した COM 定数を `$script:Xl` に追加する」と
直接衝突する(`xlCalculationManual` を追加すると `Count -eq 0` が必ず失敗する)。このテストは
T-01 時点(まだどの関数も実装されていない骨組み段階)での前提を検証するものであり、
01-design.md §6 は「実装時に実測して充填」する方針を明記しているため、実装が進んだ現時点で
このテストの前提自体が古くなっていると判断した。G-14(隣のタスクに手を出さない)の趣旨は
「関係のない関数を勝手に実装・変更しない」ことであり、自分のタスクが生んだ既存テストとの
矛盾を放置して緑を偽装することではないため、このテストの assertion を
「`$script:Xl` は今回実際に使った定数(`xlCalculationManual` 1件)だけを含む」という
G-12(実行して確認したものだけ載せる)に沿った内容に更新した。テストの構造・目的
(「無関係な定数を先回りで詰め込んでいないことの検証」)自体は保っている。

### レビュー指摘への対応(round 1、harness/state/reviews/T-03.md)

1. **[blocking] テスト準備の直接 COM 操作は G-06 の読み替え対象にならない** → **対応した**。
   `New-TestWorkbookFile` を、モジュール内部ヘルパー(`Start-XlsApplication`/`Workbooks.Add`/`SaveAs`/
   `Close`/`ReleaseComObject`/`Stop-XlsApplication` を直接呼ぶ実装)から、**公開関数
   `Invoke-XlsSession` だけを呼ぶ実装**に置き換えた。`$wb.SaveAs(...)` は `Invoke-XlsSession` の
   `ScriptBlock` の中で呼ぶため、G-06 が許す範囲(COM は `Invoke-XlsSession` の中だけ)に収まる。
   (b) のロック保持側も同様に、直接 `Start-XlsApplication`/`Workbooks.Open` を呼ぶのをやめ、
   別 STA `runspace` 上で `Invoke-XlsSession`(公開関数)を呼び出し、その `ScriptBlock` の中を
   `System.Threading.ManualResetEventSlim` 2 個(`$ready`/`$release`)で「準備完了まで待つ→
   `$app`/`$wb` を渡された `ScriptBlock` の中でロックを保持し続ける→親テストの検証が終わったら
   解放」という形にした(レビューのスニペットとほぼ同じ構成)。`BeginInvoke`/`EndInvoke` で非同期実行し、
   `finally` で必ず `$release.Set()` → `EndInvoke`(ホルダー側の `Invoke-XlsSession` が完全に
   `Quit`/`Release`/`GC×2` まで終わるのを待つ)→ `PowerShell`/`Runspace`/イベントの `Dispose` を行う。
   これでテストファイル内に直接の COM 呼び出しは一切残っていない(`Invoke-XlsSession` 経由のみ)。
   `xlOpenXMLWorkbook = 51` の直書きも、`$script:Xl.xlOpenXMLWorkbook` として `XlsAgent.psm1` の
   `$script:Xl` に追加し、`com-constants.md` にも確認日を追記して解消した(Q-3 対応)。
2. **[should-fix] finally の順序が Close→Quit→Release(逆順)→GC×2 と不一致** → **対応した**。
   `Stop-XlsApplication` に任意パラメータ `-Workbook` を追加し、`Application.Quit()` の**直後**・
   `Application` を `Release` する**前**に `Workbook` を `Release` するようにした(入れ子の `finally` で、
   `Quit` → `Release(Workbook)` → `Release(Application)` → `GC×2` のどの段が例外でも後続に確実に
   到達する)。`Invoke-XlsSession` 側は `$wb.Close($false)` の後、単に
   `Stop-XlsApplication -Application $app -Workbook $wb` を呼ぶだけにし、`Workbook` を自前で
   `Quit` より先に `Release` するコードを削除した。`Stop-XlsApplication` の `-Workbook` は省略可能な
   ので、`tests/T02.Tests.ps1` からの既存呼び出し(`Workbook` を扱わない)は無変更で動く。
3. **[should-fix] T-01 の定数件数 assertion が次タスクで再び陳腐化する** → **対応した**。
   `tests/T01.Tests.ps1` の `$xl.Count | Should Be 1` を、レビューのスニペットどおり
   `$xl.ContainsKey('xlCalculationManual') | Should Be $true` と
   `$xl.xlCalculationManual | Should Be -4135` の2つの assertion に置き換えた
   (`It` の説明も「件数固定」から「T-03 が使う既知キーの存在確認」に変更)。これにより T-04 以降で
   正当な定数が `$script:Xl` に追加されても、このテストは再度壊れない。
