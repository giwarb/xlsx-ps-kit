# T-09 Set-XlsRange

## 目的
一括書き込みの唯一の経路 `Set-XlsRange` を実装する(P3 書き込み系)。

> 01-design.md §3.5:
> ```
> Set-XlsRange -Worksheet <obj> -Range <string> (-Data <object[,]> | -FromCsv <path> | -FromJson <path>) [-Header]
> ```
> - `Value2` の 2 次元配列一括転送のみ。内部で `[object[,]]` を必ず作る。
> - CSV は UTF-8(BOM 付き)で読み書き。
> - `-Range` は左上セルだけ指定でもよい(データ寸法で自動拡張)。
> - 日付: `Set` は ISO 文字列を検出したら `[DateTime]::ToOADate()`。

- 参照ファイル: docs/01-design.md §3.5、docs/03-guardrails.md G-08
- 前提タスク: T-06(完了済み。往復対称性が受け入れ条件)
- 前提レビュー: T-01(ParameterSet 択一は確立済み)、T-06 系 r1〜r4(日付変換の罠: Date1904、条件付き書式。ただし Set 側の日付判定は「ISO 8601 文字列パターンかどうか」で行う点が Get と異なる)

## 仕様の具体化(実装判断は実装メモに記録)
- `-Data`: ジャグ配列(Get-XlsRange の戻り形式)も [object[,]] も受け付ける(型は object にして内部判定)。※T-01 の ParameterSet 骨組みでは [object[,]] 型注釈だが、Get との往復を成立させるにはジャグ配列受け入れが必要。シグネチャの型制約緩和は設計 §3.5 の「(-Data <object[,]> | ...)」の趣旨(2次元データ)の範囲内と整理してよい(実装メモに記録)。
- `-FromCsv`: UTF-8(BOM)で読む。全セル文字列になる問題への対処(数値らしき文字列を数値化するか)は実装判断(pandas の read_csv 相当の型推論の要否。方針を記録)。
- `-FromJson`: Get-XlsRange -AsJson の出力(オブジェクト配列 or 2次元配列)を受け入れて往復可能に。
- `-Header` の意味論は Get と対称に。
- ISO 日付文字列(yyyy-MM-dd / yyyy-MM-ddTHH:mm:ss)を検出したら ToOADate() で数値化。Date1904 ブックへの書き込み補正も考慮(Get 側の逆変換。Workbook.Date1904 を見る)。
- $null は空セルとして書く。
- 書き込みは常に [object[,]] を構築して Range.Value2 への 1 回の代入(G-08)。左上セル指定時は Resize で自動拡張。
- 書式(NumberFormat)は触らない(値のみ。日付書式の自動設定はしない — するなら判断を記録)。

## 実装メモ(Sonnet が記入)

### 実装の概要
`skill/scripts/XlsAgent.psm1` に `Set-XlsRange` を本実装した。既存の ParameterSet 骨組み(T-01)は
`ByData`/`ByCsv`/`ByJson` の 3 択のまま維持し、`-Data` の型注釈だけ `[object[,]]` から外した(下記)。
内部は「入力を行の配列の配列(ジャグ配列)へ正規化する」→「各セルを `ConvertTo-XlsWriteCellValue` で
Value2 に書ける値へ変換しつつ `[object[,]]` を 1 個組み立てる(`ConvertTo-XlsValue2Grid`)」→
「範囲を解決し(単一セルなら Resize)、`Range.Value2 = $grid` を 1 回だけ代入する」という 3 段構成。

### 仕様の具体化で下した実装判断
- **`-Data` の型**: 01-design.md §3.5 は `<object[,]>` だが、タスクカードの指示どおり型注釈を外し
  (`[AllowNull()] $Data` のみ)、`ConvertTo-XlsWriteRows` が実行時に形を判定する。
  1. `.Rank -eq 2` の配列 → `[object[,]]` として直接展開。
  2. それ以外の 1 次元コレクションで `-Header` 指定 → 各要素を名前付きオブジェクト
     (PSCustomObject/IDictionary)とみなし、先頭要素のプロパティ/キー順をヘッダー行にして
     `ConvertFrom-XlsHeaderObjectsToRows` で復元(`Get-XlsRange -Header` の戻り値をそのまま渡せる)。
  3. それ以外(`-Header` なし)→ 各要素をそのまま 1 行(値の配列)とみなす。要素が文字列や
     非列挙型なら「フラットな `@(1,2,3)` を 1 行 3 列/3 行 1 列のどちらとも機械的に推測しない」
     という方針で、次の一手が分かる例外にする。
- **`-FromCsv` の型推論**: pandas の `read_csv` 相当のフル型推論はせず、`Get-XlsRange -AsCsv`
  (`ConvertTo-XlsCsvField`)の出力と正確に対になる最小限だけ行う: 空文字列→`$null`、大文字小文字が
  完全一致する `'True'`/`'False'`→真偽値(`'true'` 等は文字列のまま)、不変カルチャで
  `[double]::TryParse` できる→倍精度実数、それ以外は文字列(ISO 日付判定は後段の共通変換に委ねる)。
  「テキストとして入力された "42" が CSV 往復で数値化する」という曖昧さは、CSV が型情報を保持しない
  フォーマットである以上の設計上の限界として許容する(pandas と同種の制約)。
- **`-FromJson` の形**: `-Header` なしはジャグ配列の JSON、`-Header` 付きはオブジェクト配列の JSON
  (`Get-XlsRange -AsJson` の両出力形式)を受け付ける。オブジェクト配列の復元は `-Data -Header` と
  同じ `ConvertFrom-XlsHeaderObjectsToRows` を共有する。
- **`-Header` と `-FromCsv` の組み合わせ**: 効果を持たせない(no-op)。`Get-XlsRange -AsCsv` の出力
  バイト列は `-Header` の有無で変わらない(CSV はヘッダー行かどうかを区別しないフォーマット。T-06
  実装メモ)ため、対称性を保つには Set 側も CSV の全行をそのまま書き込むのが自然と判断した。
- **ISO 日付文字列 → シリアル値**: `Test-XlsIsoDateString`(`yyyy-MM-dd` / `yyyy-MM-ddTHH:mm:ss` に
  一致するかを判定)と `ConvertFrom-XlsIsoDateStringToSerial`(T-06 の `ConvertTo-XlsIsoDateString` の
  厳密な逆関数)を新設した。逆変換規則:
  - Date1904: `dt.ToOADate() - 1462.0`。
  - 1900 年体系の架空閏日 `1900-02-29`(＋任意の時刻)は `[DateTime]` で表現できないため特別扱いし、
    serial 60(＋時刻の端数)を直接返す。
  - それ以外の 1900 年体系: `dt.ToOADate()` が `[2.0, 61.0)` の範囲(1900-01-01〜1900-02-28 の実在日付
    が写る範囲)にあれば `-1.0`、それ以外(serial 0 以下・61 以降)はそのまま。
  - 正規表現には一致するが実在しない日付(`2024-02-30` 等)は `ParseExact` が例外→ `$null` を返し、
    呼び出し元(`ConvertTo-XlsWriteCellValue`)はそのまま元の文字列を書く。
  - 純粋関数レベルで `ConvertTo-XlsIsoDateString` → `ConvertFrom-XlsIsoDateStringToSerial` の往復が
    元のシリアル値に戻ることを、境界値(1900/1904 双方)に加えてランダムでない複数の代表値で確認した
    (テストの「round-trips arbitrary serials」)。
- **`$null` → 空セル**: `ConvertTo-XlsWriteCellValue` がそのまま `$null` を通す(タスクカード指定どおり)。
- **NumberFormat は一切変更しない**(タスクカード指定)。そのため、書き込み先セルが元々日付書式で
  なければ書き込んだ日付は Excel 上では素の数値として表示される。これは仕様どおりの既知のトレード
  オフであり、テストでは「日付の往復」を検証する際に対象範囲へあらかじめ `NumberFormat` を設定してから
  `Set-XlsRange` を呼ぶ(Set はそれを一切変更しないので順序はどちらでもよい)。「NumberFormat を変更
  しない」こと自体も 1 本のテストで直接確認した。
- **寸法と自動拡張**: `-Range` の解決結果が 1x1(単一セル)のときだけ `Range.Resize(rows, cols)` で
  データの寸法に自動拡張する。複数セルの範囲を明示していてデータ寸法と一致しない場合は、両方の
  寸法を含む次の一手が分かる例外にする(異常系の受け入れ要点)。
- **行の列数不一致**: ジャグ配列の各行が同じ列数でない場合、矩形の `[object[,]]` を組み立てられない
  ため、何行目が何列だったかを含む例外にする(欠損セルを黙って `$null` 埋めしない実装判断)。
- **G-08**: `ConvertTo-XlsValue2Grid` で組み立てた 1 個の `[object[,]]` を `Range.Value2 = $grid` に
  1 回だけ代入する。関数内に `foreach` で `Cells(r,c)` へ代入する経路は存在しない。

### 踏んだ罠
1. **多次元配列インデックスをメソッド呼び出しの引数に直接埋め込むと構文エラーになる**:
   `[void]$row.Add($Array[$r, $c])` のように、カンマ区切りの多次元インデックス `$Array[$r, $c]` を
   `.Add(...)` の引数リストへ直接書くと、PowerShell のパーサーがインデックスのカンマを引数区切りの
   カンマと誤認し、「配列インデックス式の後に ']' がありません」という構文エラーになる
   (`$x = $Array[$r, $c]` という単純代入や、`foo($Array[$r, $c])`(コマンド構文の呼び出し)では
   再現しない。`.Add(($Array[$r, $c]))` のように追加の括弧で包むか、いったんローカル変数に
   取り出せば回避できる)。既存コード(T-06/T-08)にはこの埋め込みパターンがなかったため今回初めて
   踏んだ。`ConvertFrom-XlsObjectArray2DToRows` で温存変数 `$cellValue` を経由する形に直した。
   SKILL.md gotchas 候補。
2. **`.ps1`/`.psm1` に日本語コメントを書く場合、UTF-8 **BOM 付き**で保存しないと
   PowerShell 5.1 のパーサーが構文エラーを起こす**: 新規作成した `tests/Set-XlsRange.Tests.ps1` を
   BOM なし UTF-8 で書いたところ、`Invoke-Pester`/`Parser::ParseFile` 双方で無関係な位置
   (ファイル末尾付近)に「予期しないトークン '}'」という構文エラーが出た。原因は、BOM がないと
   既定の(日本語ロケールの)ANSI コードページとして読み込まれ、UTF-8 の日本語コメント中のバイト列が
   Shift-JIS 的にマルチバイト文字として誤解釈され、直後の改行バイト(0x0A)を「2 バイト文字の
   後半」として飲み込んでしまい、行がまたがって見えなくなる(`Get-Content`(既定エンコーディング)で
   数えた行数が実際より 13 行少なくなる事象で再現を確認した)。BOM 付き UTF-8 で保存し直したら
   解消した。CLAUDE.md/harness の規約(`.ps1` は UTF-8 BOM 保存)どおりだが、今回 Write ツールで
   新規作成したファイルには既定で BOM が付かなかったため、明示的に BOM を付け直す必要があった。
   SKILL.md gotchas 候補(テスト作成者向け)。
3. **`@(@(1.0, 2.0))` は内側の配列を展開して 1 段階「平坦化」される**(1 行 2 列ではなく 2 行 1 列に
   なる): 自作テストの `New-XlsObjectArray2D -Rows @(@(1.0, 2.0))` で、意図した「1 行 2 列」ではなく
   「2 行 1 列」の `[object[,]]` ができてしまい、テストが期待と違う値で失敗した。`tests/Get-XlsRange.Tests.ps1`
   が既に `@(, @(1.0, 2.0, 3.0))`(先頭にカンマ)というパターンで単一行のジャグ配列を作っているのと
   同じ理由(`@(expr)` は `expr` が既に列挙可能ならその要素を列挙して新しい配列に詰め直すだけで、
   ネストした配列をそのまま 1 要素として保持しない)。実装のバグではなくテスト側の既知の罠の踏み直し
   だったため、テストを `@(, @(1.0, 2.0))` に修正した。
4. (T-06 実装メモから踏襲・再確認)`ConvertFrom-Json` の呼び出し自体を `@(...)` で包むと二重ラップに
   なる一方、戻り値をいったん変数へ直接代入すると要素数 1 の JSON 配列は代入時にアンラップされる。
   `Import-XlsJsonRows` では `$parsedRaw = ConvertFrom-Json -InputObject $text`(直接代入、呼び出し自体は
   `@()` で包まない)→ その**変数**を `$parsed = @($parsedRaw)` で包み直す、という 2 段階パターンを
   使い、要素数 0/1/2 以上のいずれでも正しい配列になることを確認した。
5. 読み取り側(Get-XlsRange)は 1-based で Value2 の 2 次元配列を marshaling するのに対し、書き込み側
   (`Range.Value2 = [object[,]]`)は 0-based の配列を素直に受け付ける非対称性は T-06 実装メモ・
   `Common.ps1` の `New-XlsObjectArray2D` に既に記録済みで、`ConvertTo-XlsValue2Grid` も
   `[Array]::CreateInstance([object], $rowCount, $colCount)`(既定 0-based)をそのまま使い、この既知の
   非対称性を踏襲した(新たに踏んだ罠ではないが、レビュー指示に従いここでも明記)。
6. `tests/T01.Tests.ps1` の `$script:StillStubFunctions` 除外リストに `Set-XlsRange` を追加した。
   これを追加しないと「スタブ関数は throw を含む」というテストが、`Set-XlsRange` 本実装後も
   (範囲不正・寸法不一致等の正当な検証 throw のおかげで)偶然グリーンのままになり、スタブ卒業の
   事実を記録し損ねる(T-03〜T-08 が確立した既存の慣習をそのまま踏襲。T-09 固有のブックキーピングで
   あり、隣の公開関数の実装には触れていない)。

### レビュー指摘への対応（round 1、harness/state/reviews/T-09.md、判定 done・blocking ゼロ）

- **[should-fix] 「厳密な逆関数」が成立する範囲と Date1904 往復テストが不足** → 対応した。
  `ConvertFrom-XlsIsoDateStringToSerial` の `.NOTES` に「この関数が保証する往復の範囲」を追記し、
  保証対象を「`Get-XlsRange` が実際に出力しうる、秒単位・正準（canonical）な OADate」に限定する
  ことを明記した（サブ秒切り捨てと、負の小数 OADate の正準化により全 `[double]` の厳密な全単射では
  ないことを明記）。`tests/Set-XlsRange.Tests.ps1` のテスト名を
  `round-trips arbitrary serials ...` から `round-trips second-granularity canonical serials
  representable by Get ...` に変更し、コメントで保証範囲を明記した。レビュー指摘のスニペットに
  準拠した統合テスト `round-trips date-only, fictitious-leap-day, and date-time ISO strings through
  the public Set-XlsRange -> Get-XlsRange path in a Date1904 workbook`（1904-01-01・1904-02-29・
  時刻付き日時の 3 パターン、公開関数経由）を追加した。
- **[should-fix] 架空日の不正な時刻だけ未処理例外になる** → 対応した。
  `ConvertFrom-XlsIsoDateStringToSerial` の架空日 `1900-02-29` 分岐で `[TimeSpan]::ParseExact` を
  `try/catch` で囲み、失敗時は他の実在しない日付と同じく `$null` を返すようにした
  （`skill/scripts/XlsAgent.psm1`）。回帰テストを 2 本追加: 純粋関数レベルで
  `ConvertFrom-XlsIsoDateStringToSerial -Text '1900-02-29T99:99:99'` が例外を投げず `$null` を返す
  こと、`ConvertTo-XlsWriteCellValue` 経由で同じ入力が例外を投げず元の文字列のまま返ることの両方を
  確認する。
- **[should-fix] 不正 JSON フィクスチャの文字コードが暗黙** → 対応した。
  `tests/Set-XlsRange.Tests.ps1` の不正 JSON テストで
  `[IO.File]::WriteAllText($badPath, 'not valid json {{{')` に `[Text.Encoding]::UTF8` を明示した
  （レビュー指摘のスニペットどおり）。

対応後、`tests\Set-XlsRange.Tests.ps1` 単体・全体回帰とも緑（下記）で、EXCEL.EXE 残骸ゼロを確認した。
