# T-10 Test-XlsFormulas 関数

## 目的
recalc.py 互換の数式検証関数 `Test-XlsFormulas` を実装する(P4 検証系の中核)。
CLI ラッパー(T-12)と外部リンク refused(T-11)は後続タスク。本タスクは関数本体のみ。

> 01-design.md §3.6:
> - `Invoke-XlsSession -ReadOnly` で開き `CalculateFullRebuild`(`Calculation` は Automatic に一時変更)。
> - 全シートで `SpecialCells(xlCellTypeFormulas, xlErrors)`。ヒットなし例外は握りつぶす。
> - 出力 JSON(recalc.py 完全互換):
>   ```
>   { "status": "success" | "errors_found",
>     "total_formulas": int,
>     "total_errors": int,
>     "error_summary": { "#REF!": { "count": int, "locations": ["Sheet1!B5", ...], "locations_truncated": int }, ... } }
>   ```
> - G-04: キー名を変えない。locations は 100 件で切り、locations_truncated に切った数。

## 仕様の具体化(実装判断は実装メモに記録)
- 関数シグネチャ: `Test-XlsFormulas -Path <string>`(戻り値は PSCustomObject。JSON 文字列化は T-12 の CLI 側でも使うので -AsJson スイッチを付けるかは実装判断)。
- ReadOnly で開いて CalculateFullRebuild する(ファイルは変更しない — 検証専用)。
- total_formulas: 全シートの数式セル総数(SpecialCells(xlCellTypeFormulas) の Areas 集計。T-08 の Get-XlsFormulaCellKeySet 的手法を再利用してよい)。
- エラー検出: `SpecialCells(xlCellTypeFormulas, xlErrors)`(第2引数 xlErrors=16)。エラー種別は各セルの Value2(Int32 エラーコード → $script:Xl の既存定数で "#REF!" 等へ。T-06 の変換を再利用)。
- error_summary: エラー種別ごとに count / locations(`Sheet1!B5` 形式、$ なし) / locations_truncated。locations は 100 件で切る。
- locations の順序: シート順→セル順(決定的であること。テストで固定)。
- status: total_errors -eq 0 なら "success"、それ以外 "errors_found"。
- 外部リンクの refused 判定は T-11 なので今回は実装しない(構造だけ意識)。
- 数式ゼロのブック: total_formulas=0, status="success"。

## 受け入れテスト要点(02-implementation-plan.md §4)
- 意図的に `#REF!` `#DIV/0!` `#NAME?` を含むブック(Invoke-XlsSession 内で作成、Save-XlsWorkbook 経由保存)で、種別ごとの count と locations が正しい。
- 101 個以上のエラーで locations が 100 で切れ locations_truncated が正しい(1 セルずつ 101 個の数式を書くのではなく、Set-XlsRange か数式の一括代入で効率的に作る — G-08 に注意: Formula の一括代入は Value2 と別なので、範囲への同一数式一括代入 `$range.Formula = '=1/0'` が使える。実機確認して実装メモに記録)。
- 数式はあるがエラーなし → status="success"、total_formulas > 0、error_summary が空。
- 数式ゼロ → success / 0 / 0。
- Manual のまま古い値が残ったブックでも CalculateFullRebuild 後の値で判定される(T-04 の罠 5 を利用したテスト)。
- 異常系: ファイル不在で次の一手が分かる例外。

  - `-AsJson` は付けた(実装判断)。`Get-XlsModel`/`Get-XlsRange` と同じ確立済みパターン
    (`ConvertTo-Json -InputObject $result -Depth 10`)を踏襲し、T-12 の CLI 側がそのまま呼べるようにした。
  - `Get-XlsFormulaErrorCells -RangeObj <Range>`(内部、Export しない)。T-08 の

### 仕様の具体化(実装判断)
- `total_formulas`: シートごとに `Get-XlsFormulaCellKeySet -RangeObj $ws.UsedRange` の `.Count` を合算(T-08 と共有)。
- エラー種別変換: 既存の `$script:XlValue2ErrorCodes`(T-06 で整備済み)をそのまま使用。未知コードは
  `ConvertFrom-XlsValue2` と同じ規約で `"#ERR(<code>)"` にフォールバックする(情報を失わないため。
  T-08 の `.NOTES` が「厳密な検証は T-10 の責務」と書いていた箇所に対応)。
- locations の順序: `foreach ($ws in $wb.Worksheets)` のタブ順(外側)→ `Sort-Object -Property Row, Col`
  (内側、行→列の昇順)。`SpecialCells` の `Areas` 列挙順は仕様として保証されていないため、セル単位の
  行・列に分解してから明示的にソートする方式にした(Areas の走査順をそのまま信用しない)。
- `error_summary` のキー順: 上記の決定的な走査順で最初にそのエラー種別に出会った順(`[ordered]` の
  ハッシュテーブルを 2 段階(集計用 `$typeState` → 出力用 `$errorSummaryOut`)で使用)。G-04 はキー名の
  契約のみを規定しキー順までは規定していないが、決定的にしておいた。
- `locations_truncated`: `[Math]::Max(0, $entry.Count - 100)`。101 件なら 1。

### 踏んだ COM の罠(実機確認)
1. **`SpecialCells(xlCellTypeFormulas, xlErrors)` のヒットなし例外は `xlCellTypeFormulas` 単独と同じ
   HRESULT 0x800A03EC**。T-08 の `Get-XlsFormulaCellKeySet` と全く同じ catch パターン(COMException か
   つ HResult 一致のみを握りつぶし、それ以外は re-throw)を新しい内部関数 `Get-XlsFormulaErrorCells` に
   も適用した。
2. **複数セル範囲への `Range.Formula` の scalar 代入は一括操作として機能する**(実機確認)。
   `$ws.Range('A1:A101').Formula = '=1/0'` で 101 セル全てに同一の数式(相対参照なしなので実質同一)が
   適用され、`SpecialCells` で 101 件のエラーセルとして検出できた。1 セルずつのループを避けられる。
3. **複数セル範囲の `Range.Formula` の読み戻しは、セル数分だけ空白区切りで数式文字列を繰り返した文字列
   になる**(実機確認、単一セルでは単純にその数式文字列)。テストの検証ヘルパー
   (`Set-XlsFormulaVerified`)はこの非対称性のため、範囲全体の `.Formula` ではなく先頭セル
   (`Range.Cells.Item(1)`)の `.Formula` だけを読み戻して比較する設計にした。
4. **【重要】同一セッション内で複数セルへ `Formula`/`Value2` を連続して書き込んだ直後に
   `Save-XlsWorkbook` を呼ぶと、ごく稀に最後の 1〜2 セルの書き込みが保存後のファイルに反映されない**
   ことを実機で確認した(`tests/Test-XlsFormulas.Tests.ps1` の受け入れテストを複数個同じ Describe に
   並べて実行したときにだけ再現し、単独実行では再現しなかった。テストの数・内容の組み合わせに依存する
   非決定的な現象で、根本原因(Excel 内部の遅延処理か、STA スレッドの COM 呼び出しに関する何らかの
   タイミング要因か)は特定できていない)。代入直後に同じプロパティを読み戻しても未反映のまま見える
   (`xl/worksheets/sheet1.xml` を保存後に直接 ZIP で開いて確認し、`<dimension>` と `<sheetData>` に
   該当セルが本当に存在しないことまで確認した)ため、読み取り側のキャッシュや
   `CalculateFullRebuild`(`Save-XlsWorkbook` が保存前に必ず呼ぶ)の不足が原因ではない。
   `Start-Sleep`(保存直前に 500ms〜3000ms)を挟むだけでは、テストスイート全体を通しで実行したときの
   再現を安定して防げなかった。最終的に「書き込み直後に読み戻して一致することを確認し、一致しなければ
   最大 10 回(200ms 間隔)まで代入をやり直す」防御的な書き込みヘルパー(`Set-XlsFormulaVerified` /
   `Set-XlsValue2Verified`、`tests/Test-XlsFormulas.Tests.ps1` 内)で確実に反映させた。
   **SKILL.md gotchas 候補**: 複数セルへの高速な書き込みの直後に保存する場合は、最後の書き込みを
   読み戻して確認する防御的な一手が要る場合がある(単発のセル書き込みや、書き込み後に十分な処理(数式
   評価など)を挟む通常の使い方では顕在化しない可能性が高い)。今回はテストのフィクスチャ作成コードの
   みに適用し、`Save-XlsWorkbook`/`Test-XlsFormulas` 自体(数式を書き込まない読み取り専用処理)には
   影響しないため本体コードは変更していない。
5. **`Save-XlsWorkbook` は保存の度に必ず Automatic + `CalculateFullRebuild` を行う**(T-04 の設計)ため、
   「ファイルに保存された数式のキャッシュ値が実際の依存元セルの値と食い違う(Manual のまま古い値が
   残った)」状態は `Save-XlsWorkbook` 経由では作れない。受け入れ要点の「T-04 罠 5」テストは、
   `Save-XlsWorkbook.Tests.ps1` の `Get-XlsxCalcModeFromDisk`(.xlsx を COM を使わず ZIP として直接読む)
   と対になる「直接書く」版のテストヘルパー `New-XlsxWithStaleFormulaCache` を新設し、保存済み .xlsx の
   `xl/worksheets/sheet1.xml` を直接書き換えて依存元セル(A1)の値だけを変え、依存先の数式セル(A2)の
   キャッシュ済み `<v>` を古いまま残すことで再現した(COM を一切使わないので G-06 に抵触しない)。
   `xl/calcChain.xml` を残したままだと Excel がファイルを壊れているとみなすため、存在すれば
   `[Content_Types].xml`/`xl/_rels/workbook.xml.rels` の参照ごと削除する必要があることも実機で確認した。
   この状態を `Invoke-XlsSession`(Manual で開始)で開いて `Value2` を読むとキャッシュ済みの古い値が
   返り、`Set-XlsCalculationAutomatic` 相当(Automatic + `CalculateFullRebuild`)を実行して初めて
   正しい値(#DIV/0!)に更新されることを実機で確認した。
