# T-06 Get-XlsRange

## 目的
一括読み出しの唯一の経路 `Get-XlsRange` を実装する。`Value2` の 2 次元配列 → PowerShell 配列/CSV/JSON。
値変換規則(日付・空セル・エラー値)を内部関数 `ConvertFrom-XlsValue2` に集約し、T-07/T-08 が再利用する。

> 01-design.md §3.5:
> ```
> Get-XlsRange -Worksheet <obj> -Range <string> [-AsCsv <path>] [-AsJson <path>] [-Header]
> ```
> - `Value2` の 2 次元配列一括転送のみ。
> - CSV は UTF-8(BOM 付き)で読み書き。5.1 の既定エンコーディング問題を吸収。
> - 日付: `Get` は OLE シリアル → ISO 8601 文字列。

## 仕様の具体化(実装判断してよい点は実装メモに記録)
- `-Worksheet` は Invoke-XlsSession の ScriptBlock 内で得た Worksheet COM オブジェクト。
- 戻り値(既定): 2 次元をジャグ配列(行の配列の配列)で返すか `[object[,]]` で返すかは実装判断。エージェントが PowerShell で扱いやすい形を選び、理由を実装メモに書く。
- `-Header` 指定時: 1 行目をヘッダーとして扱う(CSV/JSON 出力に反映。JSON はオブジェクト配列化)。
- `-AsCsv <path>` / `-AsJson <path>`: ファイルに書き出し(UTF-8 BOM 付き)。両方同時指定の扱いは実装判断。
- 日付判定: Value2 は日付もただの Double。セルの NumberFormat が日付書式かどうかで判定する(方式は実装判断、確実な方法を選び実装メモに記録)。ISO 8601 文字列("yyyy-MM-ddTHH:mm:ss" 等)に変換。
- 空セル: `$null` を維持。
- エラー値(#REF! 等): Value2 は Int32 のエラーコードを返す。文字列表現("#REF!" 等)に変換するか、そのまま返すかは実装判断(recalc 検証は T-10 が担当するため、ここでは「読める」ことが重要)。
- 単一セル範囲: Value2 が 2 次元配列でなくスカラーで返る点に注意(既知の COM 罠)。

## 実装メモ(Sonnet が記入)

### 実装判断（仕様の具体化）

- **戻り値の形**: 既定はジャグ配列（行の配列の配列）。`[object[,]]` にしなかった理由は、
  エージェントが `$rows[0][1]` のように素直にインデックスでき、`ConvertTo-Json` への受け渡しも
  自然になるため（`[object[,]]` は PowerShell では扱いにくく、`ConvertTo-Json` も正しく扱えない）。
- **-Header の適用範囲**: 戻り値と `-AsJson` の両方に一貫して反映する（1 行目をヘッダー名として
  読み飛ばし、`PSCustomObject` の配列にする）。`-AsCsv` の出力バイト列は `-Header` の有無で変わらない
  （CSV はそもそも「1 行目がヘッダーか」を区別しないフォーマットで、ジャグ配列にはヘッダー行を
  含む全行がそのまま入っているため、書き出す内容は同じになる。取り違えではなく意図した挙動）。
- **日付判定方式**: `Range.NumberFormat` の文字列にトークン文字（d/m/y/h/s）が含まれるかで判定する
  （`Test-XlsIsDateNumberFormat`）。`'General'` とのリテラル一致にしなかった理由は下記の COM の罠を参照。
- **エラー値の表現**: `"#REF!"` 等の表示文字列に変換する（Value2 の生の Int32 のままでは可読性が
  低く、CSV/JSON にそのまま出しても意味が伝わらないため）。既知 7 種以外は情報を失わず
  `"#ERR(<code>)"` にフォールバックする。
- **単一セル範囲のスカラー対策**: `ConvertFrom-XlsRangeToRows` で `$raw -isnot [Array]` により
  スカラー/2 次元配列を判定し、常に 1 行 1 列のジャグ配列に正規化する。
- **ヘッダーセルが空/重複**: 空/`$null` は `"Column<列番号(1始まり)>"` に置き換え、重複キーは
  `[ordered]` ハッシュテーブルで後勝ち。仕様に明記がないための実装判断。
- **-AsCsv と -AsJson の同時指定**: 両方許可し、両方のファイルを書き出す（排他にする理由がない）。

### 踏んだ COM の罠（SKILL.md gotchas 候補、実機確認済みのみ）

1. **既定の「標準」書式が英語の `'General'` ではなくローカライズされた文字列で返る**:
   日本語ロケールの Excel では、既定セルの `Range.NumberFormat`（本来カルチャ非依存のはずの
   プロパティ）が `"G/標準"` として返ってくることを実機で確認した。`'General'` とのリテラル比較で
   日付判定すると、ロケール次第で常に false 判定になり得ない（このケースでは偶然 d/m/y/h/s を
   含まないため安全だったが、リテラル比較そのものが信頼できないと判断し、トークン文字方式にした）。
   さらに、`NumberFormat = 'General'` への**書き込み**はこの環境で常に失敗した
   （`Range クラスの NumberFormat プロパティを設定できません`）。空文字列 `''` を設定すると
   `'G/標準'` に戻ることを確認した（T-09 Set-XlsRange 向けの参考情報として記録）。
2. **`Range.Value2` の 2 次元配列は 1-based**: `.GetLowerBound(0)`/`.GetLowerBound(1)` がともに 1
   になる（.NET の既定である 0-based ではない）。0 起点を仮定して `$raw[0,0]` のようにアクセスすると
   `IndexOutOfRangeException` になる。`Range.Cells.Item(r,c)` の `r,c` も同じ範囲相対 1-based
   インデックスであることを確認済み（`Worksheet.Range('B3:D5')` のような非 A1 起点の範囲でも
   `Cells.Item(1,1)` が範囲の左上 `$B$3` を指すことを実機で確認した）。
   **一方、書き込み側（`Range.Value2 = [object[,]]`）は 0-based の配列（`[Array]::CreateInstance` の
   既定）をそのまま受け付ける**。読みと書きで前提となる境界が非対称な点に注意（T-09 で要注意）。
3. **`Range.NumberFormat` は複数セルの範囲で一括 2 次元配列にならない**: 範囲内の書式が
   すべて同一ならスカラー文字列 1 個、1 つでも異なれば `[DBNull]::Value` を返す。`Value2` と違って
   セル単位に展開されない。まず一括読みを試し、`DBNull` のときだけセル単位
   （`Range.Cells.Item(r,c).NumberFormat`）にフォールバックする 2 段構えにした（書式が範囲全体で
   統一されている多くの実データではセル単位アクセスが発生しない）。既知の制約: 混在時は
   セル数分の COM 呼び出しが発生し、大きい範囲では遅くなり得る。列単位の最適化は今回のスコープでは
   見送った（ヘッダー行を含む列は多くの場合その列内でも書式が混在するため、単純な列単位読みでは
   効果が薄いと判断した）。
4. **`Range.Value2` の .NET 型がセル種別を一意に表す**: 数値・日付は必ず `[double]`
   （整数値でも `[int]` にはならない）、文字列は `[string]`、論理値は `[bool]`、エラー値だけが
   `[int]`（CVErr の Long 表現）。この型判定だけでエラー値かどうかを一意に判定できる（値の大小や
   別プロパティの取得が不要）。実機で 7 種類のエラー値（`#NULL!` `#DIV/0!` `#VALUE!` `#REF!`
   `#NAME?` `#NUM!` `#N/A`）の Int32 コードを確認し、`$script:Xl`/`com-constants.md` に記録した。
5. **無効な範囲アドレスは `Worksheet.Range(...)` 自体が例外を投げる**（`.Value2` へのアクセス時では
   ない）。生の COM 例外は `Exception from HRESULT: 0x800A03EC` のみで手がかりがないため、
   `Get-XlsRange` は `Worksheet.Range()` の呼び出しを try/catch し、範囲文字列とシート名を含む
   次の一手が分かる例外に包み直す。

### 踏んだ PowerShell（非 COM）の罠

6. **`Invoke-XlsSession` の `return & $ScriptBlock $app $wb` が要素数 1 の配列を剥がしてしまう
   不具合を発見・修正した（T-03 の既存コード）**: ScriptBlock の戻り値が「要素数 1 の配列」
   （例: 単一行だけのジャグ配列）のとき、`return` の内部的な出力ストリーム展開（`Write-Output` と
   同じ、配列を 1 段階だけ展開する挙動）がその外側の配列を剥がし、呼び出し元には配列の中身が
   そのまま渡ってしまうことを実機で確認した（2 要素以上の配列では両方とも同じ個数として観測される
   ため症状が出ず、T-03〜T-05 のテストでは一度も踏まれていなかった。文字列やオブジェクト単体しか
   返してこなかったため）。単項カンマで 1 段階だけ包み直す `return , (& $ScriptBlock $app $wb)` に
   修正した（このファイル内の `Clear-XlsOrphans` の `return , $results` と同じ、既存の確立済み
   パターンを踏襲）。scriptblock がスカラーを返す既存の T-03 テスト（(d) 受け入れ要点）は
   影響を受けないことを確認済み（スカラーは 1 段階の展開で往復しても変化しない）。
   G-14 は「隣の関数に手を出さない」だが、これは T-03 の受け入れ要点 (d)「戻り値が透過する」
   そのものが、配列の場合に成立していなかったという不具合修正であり、T-06 の
   `Get-XlsRange`（単一行のジャグ配列を返す）が初めてこの不具合を露呈させたため、実装メモに
   詳細を記録した上で最小限の 1 行修正のみ行った。`tests/Invoke-XlsSession.Tests.ps1` の既存テストは
   変更しておらず、全回帰緑を確認済み。
7. **`$result = if (cond) {...} else {...}`（if/else を式として使う代入）が、選ばれた枝の値が
   「要素数 1 の配列」で、かつその配列が既に 1 回関数の `return ,` 境界を通過済みの値だった場合、
   もう 1 段階多く展開して中身を剥がしてしまうことを実機で確認した**（同じ配列をその場で
   インライン生成した場合は再現しない。ローカル変数への代入元がどこかで関数境界をまたいだかどうかで
   挙動が変わる、紛らわしい罠）。`Get-XlsRange` 内部でこれを踏み、`if (...) { $result = A } else
   { $result = B }`（式ではなく文として使う形）に変更して回避した。
8. **`@( コマンド呼び出し | ConvertFrom-Json )` は要素数が壊れる**: `ConvertFrom-Json` は JSON 配列を
   パイプラインへ「展開せず 1 個のオブジェクトとして」書き出すため、`@( )` でコマンド呼び出しを
   直接包むと、そのパイプライン出力（1 個の配列オブジェクト）がさらに 1 段階配列に包まれてしまう
   （`@(変数)` のように既に受け取った変数を包む場合はこの問題が起きない）。テストコードでの
   ハマりどころとして記録（モジュール本体はこのパターンを使っていない。`Export-XlsJson` は
   `ConvertTo-Json -InputObject $Data`、`ConvertTo-Json` 側で確認、パイプでなく名前付き引数を
   使うことで別の既知の単一要素アンラップ問題を避けている）。
9. **Pester 3.4 の `Should Contain` は「コレクションに要素が含まれるか」ではない**: パイプ元を
   ファイルパスとみなし、その中身に文字列/正規表現がマッチするかを見るアサーションだった
   （実機で `$props | Should Contain 'Name'` を書いたところ、`$props` の中身をファイルパスとして
   `Get-Content` しようとして例外になった）。配列の要素判定には `-contains` 演算子を使う。

### [blocking 2] Date1904・1900 年 1〜2 月の未対応 → 対応した

新規内部関数 `ConvertTo-XlsIsoDateString`（`ConvertFrom-XlsValue2` から呼ぶ）に、OADate 変換の補正を
集約した。実装前に実機で検証した事実（`scratchpad` の使い捨てスクリプトで、新規ワークブックのセルに
直接シリアル値を入れ `Range.Text` の表示と `[DateTime]::FromOADate()` を比較。実装メモの
`ConvertTo-XlsIsoDateString` の `.NOTES` に詳細を転記済み）:
- 1904 体系（`Workbook.Date1904=$true`）: シリアル値 +1462 で `FromOADate` と Excel の表示が一致する
  （serial 0/1/59/60/61/367 で確認）。1904 年は実在の閏年のため、1900 年体系のような架空日補正は不要
  （実機確認）。
- 1900 体系（既定）: シリアル 1〜59 は `FromOADate` の結果が Excel の表示より 1 日少ないため +1 の
  補正が必要（serial 1/2/59 で確認）。シリアル 61 以降は補正なしで一致する（serial 61/367 で確認）。
- シリアル 60 は Excel が `1900-02-29`（実在しない架空の閏日）と表示する。`FromOADate` はこの日を
  作れないため、整数部が 60 の間は文字列 `"1900-02-29"` を固定で使い、端数（時刻）があれば ISO 形式で
  付加する（レビュー指摘どおり方針を明文化）。

`Get-XlsRange` は `$Worksheet.Parent.Date1904` を 1 回だけ読み（`Worksheet.Parent` が所属 Workbook を
返すことを実機確認済み）、`ConvertFrom-XlsRangeToRows` → `ConvertFrom-XlsValue2` へ `-Date1904` スイッチ
として引き渡す。

境界テスト（serial 1/59/60/60.5/61、Date1904 の serial 0/59）と、Date1904 ワークブックを使った
`Get-XlsRange` の統合テストを追加し、緑を確認した。

### [should-fix 1] Invoke-XlsSession の戻り値ストリーム契約が未固定 → 対応した

`Invoke-XlsSession` の `.NOTES` に「`ScriptBlock` の戻り値は非列挙の単一の値として扱い、ストリーム
透過（複数回パイプライン出力したものを呼び出し元が個別に受け取れること）は保証しない」契約を明文化した
（01-design.md §3.1 の「戻り値をそのまま返す」を配列にも一貫させる意図的な契約であることを明記）。
`tests/Invoke-XlsSession.Tests.ps1` の (d) に、スカラー（既存）に加えて「要素数 1 の配列」「要素数 2 以上
の配列」「`ScriptBlock` が複数回パイプライン出力した場合に 1 個の `object[]` へまとまる」の 3 パターンを
追加し、緑を確認した。レビューが挙げた「ストリーム透過を契約にするならこの 1 行を戻す」という代替案は
採らなかった。理由: ストリーム透過性（`Invoke-XlsSession ... | ForEach-Object` で個別に受け取れること）
を維持すると、T-06 の受け入れ要点である「単一行のジャグ配列を 1 個の値として返す」が再び壊れる
（round 1 で発見した不具合そのもの）。01-design.md §3.1 は「ScriptBlock の戻り値をそのまま返す」としか
書いておらず、複数パイプライン出力時の挙動までは既定していないため、G-01（確定事項変更）には当たらない

## round 4 レビュー対応（harness/state/reviews/T-06-r3.md、判定 fix、blocking 1）

### [blocking] 全セクション条件付き・全条件不一致時に偽の条件付きセクションへフォールバックする → 対応した

`Select-XlsNumberFormatSection` の最終フォールバックを `return $Sections[0]`（round 3 の「縮退ケース」
実装判断）から `return $null` に変更した。

指摘の core: `'[<0]yyyy-mm-dd;[>100]0.00'` と値 `50` は、`<0` も `>100` もどちらも偽であり、Excel は
どちらの数値表示も適用しない。それにもかかわらず機械的に `$Sections[0]`（今回はたまたま日付
セクション）へ戻すのは、round 3 で修正した「符号で決め打ちして誤判定する」問題と同じ種類の誤り
（適用されるべきでないセクションを選んでしまう）を作っていた。「全セクション条件付き・全条件不一致」は
Excel の書式仕様上は正規化されていない縮退ケースだが、レビュー指摘のとおり `$null`（＝「どのセクションも
適用されない＝日付トークンなしとして扱う」）に倒すのが安全側の判断として正しいと判断した。

呼び出し元 `Test-XlsFormatSectionHasDateToken` は `[AllowNull()][AllowEmptyString()]` 済みで
`[string]::IsNullOrEmpty($Section)` を先頭でチェックしているため、`$null` を渡しても安全に
「日付トークンなし（$false）」として扱われることをコードで確認済み（変更不要）。

レビュー記載の回帰テスト（`'[<0]yyyy-mm-dd;[>100]0.00'` + 50 → false）をそのまま追加し、緑を確認した。

### round 4 で新たに踏んだ罠（SKILL.md gotchas 候補）

14. **条件付き数値書式で全セクションが条件付き、かつどの条件にも一致しない場合、Excel の書式仕様は
    「残りの数値をどう表示するか」を規定していない縮退ケースになる**。実装上、安全側に倒す（＝
    どのセクションも適用しない扱いにする）べきで、機械的に先頭セクションへフォールバックすると、
    そのセクションがたまたま日付書式だった場合に誤変換を起こす。「一致しないなら何もしない」を
