## 指摘

### [blocking] 複数セクションを持つ有効な日付書式を非日付と判定する

- 場所: `skill/scripts/XlsAgent.psm1:704`
- 内容: `@` が文字列のどこかにあるだけで `$false` を返すため、一般的な `m/d/yyyy;@` が非日付扱いになり、`45000` が ISO 8601 へ変換されず生値のまま返る。Excel の書式は正数・負数・ゼロ・テキストの最大 4 セクションであり、`@` はテキスト用セクションに存在しても数値セクションの日付性を否定しない。また、角括弧の一律除去は `[h]` 単独の経過時間を失い、バックスラッシュでエスケープされた `0\m` は逆に日付と誤判定する。[Microsoft の書式仕様](https://support.microsoft.com/en-US/Excel/review-guidelines-for-customizing-a-number-format)とも不一致で、日付変換契約への逸脱。
- 修正案: 値に対応する数値セクションだけを選び、引用文字列、`\`、`_`、`*` の次の文字をリテラルとして除外するトークナイザーにする。`[h]`/`[m]`/`[s]` は日付・時刻トークンとして残す。最低限、次をテストに追加する。

```powershell
Test-XlsIsDateNumberFormat -NumberFormat 'm/d/yyyy;@'  # $true
Test-XlsIsDateNumberFormat -NumberFormat '0\m'         # $false
Test-XlsIsDateNumberFormat -NumberFormat '[h]'         # $true
```

### [blocking] Workbook.Date1904 と 1900 年 1～2 月を考慮していない

- 場所: `skill/scripts/XlsAgent.psm1:767`
- 内容: `[DateTime]::FromOADate($Value2)` は通常の 1900 日付体系の現代日付には正しいが、1904 日付体系では同じ日付のシリアルが 1462 日異なるため、約 4 年ずれた ISO 文字列を返す。また Excel と OLE Automation は 1900 年の最初の 2 か月にも差異がある。Microsoft も `FromOADate` の例がこの二点を扱わないと明記している。[Value2 と OA Date の説明](https://learn.microsoft.com/en-us/visualstudio/vsto/how-to-programmatically-store-and-retrieve-date-values-in-excel-ranges?view=visualstudio)、[Excel の 1900/1904 日付体系](https://support.microsoft.com/en-us/office/change-the-date-system-format-or-two-digit-year-interpretation-aaa2159b-4ae8-4651-8bce-d4707bc9fb9f)
- 修正案: `ConvertFrom-XlsRangeToRows` で `Workbook.Date1904` を一度取得し、内部変換関数へ渡す。1904 体系では 1462 を加算し、1900 体系の serial 1～59 は OA Date との差を補正する。serial 60（Excel の架空の 1900-02-29）は返却方針を明文化する。

```powershell
$oaValue = [double]$Value2
if ($Date1904) {
    $oaValue += 1462
}
elseif ($oaValue -ge 1 -and $oaValue -lt 60) {
    $oaValue += 1
}
elseif ($oaValue -ge 60 -and $oaValue -lt 61) {
    # serial 60 の方針を明示: 生値維持、専用文字列、または明示的エラー
}
$dt = [DateTime]::FromOADate($oaValue)
```

1904 体系の統合テストと、1900-01-01/1900-02-28/serial 60 の境界テストも必要。

### [should-fix] Invoke-XlsSession の修正は妥当だが出力ストリームの意味が変わる

- 場所: `skill/scripts/XlsAgent.psm1:402`
- 内容: `return , (& $ScriptBlock ...)` は、T-06 の単一行・単一セルのジャグ配列を一つの値として保つ目的には妥当で、スカラーや代入で受ける複数要素配列にも問題はない。一方、ScriptBlock が `1; 2` のように複数のパイプライン出力を生成した場合、それらを一つの `object[]` にまとめ、`Invoke-XlsSession ... | ForEach-Object` から見える要素数を N から 1 に変える。既存テストはこの公開関数のストリーム挙動を固定していない。
- 修正案: T-03 のテストにスカラー、単一要素配列、複数要素配列、複数パイプライン出力を追加する。その上で「ScriptBlock の戻り配列を非列挙で一つの値として返す」を意図するなら、§3.1 とコメントベースヘルプにも明記する。ストリーム透過を契約とするなら、この 1 行は戻して T-06 側で形状を保持する必要がある。

### [should-fix] DBNull フォールバックが一般的な表でもセル数比例の COM 呼び出しになる

- 場所: `skill/scripts/XlsAgent.psm1:840`
- 内容: 二段構え自体は正しく、全セル同一書式なら NumberFormat の COM 読み取りは 1 回。ただし混在時は `1 + 行数×列数` 回になり、ヘッダーが General、本文に日付列がある通常の表でも直ちにフォールバックする。さらに文字列・空セル・真偽値・エラー値にも NumberFormat を取得しているが、日付判定に必要なのは `[double]` だけ。Excel が混在範囲の NumberFormat を Null とすること自体は仕様どおり。[Range.NumberFormat](https://learn.microsoft.com/en-us/office/vba/api/excel.range.numberformat)
- 修正案: 最低限、混在時のセル別 NumberFormat 取得を `[double]` に限定し、`$null` と `[DBNull]` の両方を混在扱いにする。

```powershell
$useUniformFormat = ($null -ne $bulkFormat -and $bulkFormat -isnot [DBNull])

$nf = ''
if ($cellValue -is [double]) {
    if ($useUniformFormat) {
        $nf = $bulkFormat
    }
    else {
        $nf = $RangeObj.Cells.Item($r, $c).NumberFormat
    }
}
```

大規模な数値表まで考慮するなら、行・列または範囲を分割して一括 NumberFormat を再試行し、均一な部分範囲をキャッシュする方式が望ましい。

### [nit] CSV の改行エスケープをテスト名だけで実データに含めていない

- 場所: `tests/Get-XlsRange.Tests.ps1:186`
- 内容: テスト名は comma・double quote・newline を検証するとしているが、入力 `'a,b"c'` に改行がない。実装の `[",\r\n]` と引用符二重化はコード読解上正しく、BOM・CRLF 生成も正しいが、回帰テストが改行を固定していない。
- 修正案:

```powershell
$value = "a,b`r`n`"c"
$result = & $script:ModuleRef {
    param($v) ConvertTo-XlsCsvField -Value $v
} $value
$result | Should Be "`"a,b`r`n`"`"c`""
```

- `Value2` の日付シリアル変換では `Workbook.Date1904` と 1900 年 1～2 月の Excel/OA Date 差異を考慮する。
- PowerShell の単項カンマによる配列保持は、呼び出し元がパイプで受けた場合の出力個数も変える。配列同一性とストリーム透過性のどちらを契約にするか明示する。
